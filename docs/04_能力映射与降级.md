# 能力映射、参数回退与模型降级

> **性质**：适配层**策略层**的设计真源。它不改目标契约（`docs/seedance-api-reference.md` 仍是
> 唯一真源），也不改上游契约（`docs/upstreams/aivideomaker-official-api.md`）；
> 它规定的是**两者的差值怎么处理、怎么上报**。
> **上游侧现状**：`script_store/aivideomaker/video@v1.py` 已实现本文 §1/§2 的一部分
> （正则映射 + 就近吸附 + `warnings[]`）；本文指出它**缺什么、错在哪**，以及应当长成什么样。
>
> 关联：`docs/adapter-playbook.md` §3.2（判定准则）、§4（顶层参数降维）、§8（计费护栏）；
> `ADR-002`（路由与 provider）、`ADR-004`（支出上限）。

---

## 0. 先切开三层，否则会做出一台「静默换模型」的机器

「映射 / 降级 / 回退」听起来是一件事，实际是**三个不同的层**，代价与可逆性完全不同：

| 层 | 变化的是什么 | 调用方能察觉吗 | 危险度 |
| --- | --- | --- | --- |
| **L1 路由映射** | 调用方写的名字 → 打到哪个上游的哪个模型 | 看响应回显 | 🔴 高：**错映射 = 误路由 = 直接付费** |
| **L2 参数回退** | 同一个模型下的**取值**（时长/清晰度/比例） | 看响应字段 | 🟡 中：可能**跨档涨价** |
| **L3 模型降级** | **模型身份本身** | 只能靠上报 | 🔴 高：等同**换供应商** |

> 🔴 **铁律：三层不得互相代替。**
> 最典型的错误正是"参数回退不了 ⇒ 悄悄换个模型"—— 那等于让 **L2 的失败触发 L3**，
> 而调用方从未同意换上游。**这三层的授权是独立的**：同意"时长可以取整"绝不等于
> 同意"可以换成另一个厂商的模型"。

另外一条贯穿全文的方向性判据（沿用 playbook §3.2）：

> **改完这一项，会不会改变"用户想要什么"？**
> 会 → `400`；不会（只是画质/编码/风格层面的弱化）→ 回退 + **如实上报**。

## 1. L1 路由映射：写成声明表，不要靠正则猜

### 1.1 矛盾点：目标侧是「具体模型 ID」，上游侧是「8 个粗槽位」

目标契约 §7.1 规定调用方写的是**具体模型 ID**：

`doubao-seedance-2-5-260628` / `…-2-0-260128` / `…-2-0-fast-260128` / `…-2-0-mini-260615` /
`…-1-5-pro-251215` / `…-1-0-pro-250528` / `…-1-0-pro-fast-251015`

而上游只有 8 个粗槽位（`t2v` / `i2v` / `t2v_v3` / `i2v_v3` / `minimax` / `seedance20` /
`wan27` / `happyhorse`）。**这个降维天然有损**，且损失有两类，必须分开对待：

- **可接受的损失**：同一能力面内的版本/规格差异（例如 `2.0` 与 `2.0 mini` 都文生视频）。
- **不可静默的损失**：**换了模型身份**（版本代差、甚至换了厂商）。

⚠️ 已知观测（`~/.workbuddy/skills/aivideomaker-api` 的计费实验）：上游 `t2v` 槽位的**实际产出**
来自 **minimax_h3**（成品 URL 可见），且码率约为 `seedance20` 的 1/4.8。
⇒ 把某个便宜档当成"Seedance 的便宜版本"是**错觉**：它是**另一个厂商的模型**。
这类映射一旦发生，**必须进 L3 降级报告**，不能只算作"档位差异"。

### 1.2 建议映射表（**对 aivideomaker 官方线**；落位见 §7 待定 3）

| Seedance 模型 ID | 请求需要的核心能力 | 建议上游槽位 | 性质 | 依据 |
| --- | --- | --- | --- | --- |
| `doubao-seedance-2-5-260628` | 全套（文/首尾帧/参考图≤9/视频≤3/音频≤3/编辑/延长） | **无对应**：上游 API 最高只有 `seedance20` | 🔴 **版本降级**（2.5→2.0）；含 2.5 独有能力时 **400** | 上游 §4.5 + 目标契约 §7.2 |
| `doubao-seedance-2-0-260128` | 同上（参考类上限更小） | `seedance20` | ✅ 直映；但**参考图 >1 张 / 视频 >1 段 / 音频 >1 个**时上游只有单值 ⇒ 400 或显式降级到 `minimax`（≤4 图 / ≤2 音频） | 上游 §4.5 |
| `doubao-seedance-2-0-fast-260128` | 上限 720p，无 4k | `seedance20`（`resolution=720`） | 🟡 **规格降级**：请求 1080p ⇒ **400**（fast 不支持），不得悄悄降到 720p（那是 L2，需要授权） | 目标契约 §7.2 |
| `doubao-seedance-2-0-mini-260615` | 上限 720p | `seedance20`（`resolution=720`） | 同 fast | 目标契约 §7.2 |
| `doubao-seedance-1-5-pro-251215` | 参考图、生成有声 | `minimax`（唯一全能力槽位） | 🔴 **跨厂商降级**；若纯文生则 `t2v_v3` 亦可（更便宜） | 上游 §4.4 |
| `doubao-seedance-1-0-pro-250528` | 文生 / 首尾帧 | `t2v`（纯文生）；需尾帧 ⇒ `minimax` | 🔴 `t2v` 是**跨厂商**（实测底层 minimax_h3）⇒ 必须上报 | 上游 §4.1/§4.4 |
| `doubao-seedance-1-0-pro-fast-251015` | 无首尾帧 | `t2v` | 🔴 同上；`fast` 语义 ⇒ 落**便宜档**（playbook §8.1） | — |

### 1.3 规则

1. **表由渠道声明**（`X-Channel-Options.model_map`），脚本**只执行、不猜**。
   现状是脚本内 `_MODEL_PATTERNS` 正则 + **顺序敏感** —— 调换两行就静默错映射，
   且调用方无法预知"我写这个名会打到哪"。表外置后：同一份脚本服务多个上游，新增上游不改脚本。
2. **未命中 ⇒ 400 + 列出可用名**（与现状一致，**绝不兜底**；v1 已删掉旧实现的
   `return "seedance20"` 兜底 —— 那是"写错一个字母就直接付费"的入口）。
3. **歧义（命中多条）⇒ 400 + 列出候选**。歧义不猜：`2.0` 既可能指标准版也可能指 fast，
   代价差好几倍。
4. 通配键（`*seedance*`）**优先级低于精确键**，按**最长匹配**胜出。
5. **命中哪条规则必须进上报**（`model.map.hit`）—— 否则"为什么这个请求打到 `t2v`"
   没人答得上来。
6. **映射表不得跨 `provider`**（沿用 ADR-002）：表里的目标槽位必须属于本渠道声明的 provider。

## 2. L2 参数回退：方向由**成本**决定，不是由"谁离得近"决定

### 2.1 现状与缺口

`video@v1.py::resolve_duration` 对离散档位用 `min(allowed, key=(abs(a-value), a))`
—— **就近吸附、平局向下**。于是：

| 输入 | t2v（5, 8，每秒 3 积分） | 判定 |
| --- | --- | --- |
| `6s` | → `5s`（15 积分） | ✅ **便宜**，即用户举的 `6s=>5s` |
| `7s` | → `8s`（24 积分） | ⚠️ **涨价 +60%**，只发了一句 warning，**不回看 `max_credits`** |

⇒ 缺口是**方向失控**：`6→5` 恰好对，`7→8` 恰好错，而决定两者的只是"哪一个更近"。
**"更近"不是一条安全准则，成本才是。**

### 2.2 两个正交的轴

| 轴 | 取值 | 语义 | 默认 |
| --- | --- | --- | --- |
| `fallback_direction` | `down` | 只允许落在**不长于/不高于/不宽于**请求的档位 | ✅ **默认** |
| | `nearest` | 就近（现行行为），**允许向上** | |
| | `up` | 只允许向上（"至少这么长"的场景） | |
| `fallback_policy` | `adjust` | 回退并如实上报 | ✅ **默认** |
| | `strict` | **不回退**，直接 `400`（调用方要精确值时用） | |

默认组合 `down + adjust` 的直接结果：

- `6s → 5s` ✅（用户要的）
- `7s → 5s` ✅（**不再是 8s**；宁可短，也不悄悄多花钱）
- `21:9 → 16:9` ✅（更窄，不是"更接近的那个"）
- `2s` 对 `happyhorse`（区间 3–15）⇒ **400**（向下无解、又未授权向上）

> **为什么默认 `down`**：向上回退是**静默涨价**，与本项目"支出上限是提交前置条件"（ADR-004）
> 属于同一类风险；向下回退只改变产品规格，**永远不在账单上给惊喜**。
> 要 `7→8` 的调用方显式给 `fallback_direction: "nearest"` 即得。

### 2.3 三类取值的各自规则

**a) 离散档位**（`t2v`/`i2v` 5|8、`*_v3` 5|10|15|20、`wan27` 5|10|15）
按 `direction` 在允许集里选：`down` 取 **≤ 请求值的最大档**（不存在则 400）；
`up` 取 ≥ 请求值的最小档；`nearest` 就近。

**b) 连续区间**（`minimax` 5–20、`seedance20` 4–15、`happyhorse` 3–15）
**维持钳制，不做吸附**（`v1` 已对）。但**钳制向上同样会涨价**，所以也要受方向约束：
`down` 模式下低于下界 ⇒ **400**（不得自动抬到 `min`）；高于上界 ⇒钳到 `max`（那仍是向下）。
⚠️ `duration: -1`（模型自选）目标契约支持、上游 8 个模型**都不支持** ⇒ 必须替换成具体整数
（建议：区间类取 `min`，并上报 `requested:-1 → effective:<min>`）。

**c) 比例（`ratio`）**
`adaptive` 的原意是"跟着输入素材走"，**落 `16:9` 是在替调用方猜**，而竖屏素材上
`adaptive` 与 `16:9` 是**两个不同的产品**。规则：

| 情况 | 处理 |
| --- | --- |
| 有首帧图 | 从**图片实际尺寸**反推比例（playbook §4 已写，v1 未实现 ⇒ 待补） |
| 无首帧图 + 上游支持自选（`minimax` 的 `auto`） | 原样映射 `auto` |
| 无首帧图 + 上游不支持自选 | **400**（不再默认 `16:9`）；显式 `fallback_direction` 授权后才落具体比例 |
| 具体比例不在允许集（如 `21:9` 对 `wan27`） | 按 §2.2 的方向规则吸附 + 上报 |
| 模型**没有**比例字段（`i2v` 系） | 不发该字段 + 上报 `param_ignored`（发未文档化字段会 `INVALID_PAYLOAD`） |

### 2.4 🔴 顺序：先定最终取值 → 再估成本 → 再比上限 → 才发上游

回退**必须**在上限判断之前完成，并在**回退后的取值**上重新估算：

```
请求 → (1) 解析映射(L1) → (2) 参数回退/钳制(L2) → (3) [可选] 能力缺口降级(L3)
     → (4) 用最终取值估成本 → (5) 比 max_credits → (6) 提交上游
```

现状的缺口：`7→8` 时若 `max_credits` 恰好卡在 5s 的价钱上，调用方会收到一个指向
**`duration`** 的 400，而真实原因是"适配层替你升了一档"。正确做法是**在 (2) 就拒绝**，
并在 message 里说明"向上回退会超出上限"。

## 3. L3 模型降级：只允许「能力驱动」，且必须声明链

### 3.1 唯一判据

> **把一个诉求交给另一个模型，会不会改变"用户想要什么"？**
> 会 ⇒ **400**，并把差异**如实说出来**（"该模型不支持参考音频；上游唯一能接参考音频的槽位是
> `minimax`，是否改用它？"）。
> 不会（只是画质/编码/风格的弱化）⇒ 可降级，但必须**显式声明链 + 单独上报 + 不得涨价**。

### 3.2 五种**禁止**触发降级的情形（这一节是全文最贵的部分）

| # | 情形 | 为什么不能降级 | 正确做法 |
| --- | --- | --- | --- |
| 1 | 上游 **5xx / 429 / 超时 / 连不上** | 那是**可用性**问题。换模型会让调用方拿到**另一个厂商的产出**却毫无察觉；而它本可以重试拿到原本要的东西 | 退避/重试（限流走 §7.1 的冷却），最终如实报错 |
| 2 | 请求**超出 `max_credits`** | 换便宜模型 = 悄悄改产品来迁就预算 | **400**，让调用方自己决定是加预算还是改需求 |
| 3 | 请求含**参考类素材**而目标模型接不住 | 丢参考素材改变的是"这是不是你想要的"，不是画质 | **400**（playbook §3.2 的铁律） |
| 4 | 目标模型**能力更弱**（如 `2.0` 的请求降到不支持首尾帧的槽位） | "降级"却丢了能力，等于换了个残缺的实现 | 沿链继续找**能力 ⊇ 需求**的目标；找不到就 400 |
| 5 | 目标是**另一个 provider** | 跨 provider = 跨合同/跨计费主体，必须由调用方重新发请求（ADR-002） | 400 |

⚠️ 唯一的例外是**已有明确决定**的两处，且它们必须在 `degradations[]` 里单独标注：
**尾帧在单图上游上可丢**（playbook §3.1 已定：取首帧 + warning）—— 但因为它决定**结束画面**，
必须作为 `capability_dropped` 结构化上报，不能只混在人类可读的 `warnings[]` 里。

### 3.3 降级链的声明与三条约束

```jsonc
// X-Channel-Options.fallback_chain —— 有序；只在 when 命中时按序尝试
"fallback_chain": [
  {"model": "minimax", "when": ["capability_gap:reference_audio", "ref_image_gt_1"]},
  {"model": "t2v",     "when": []}      // 空 when = 不可作为降级目标（只能被显式指名）
]
```

1. **只在 `when` 命中时触发**，`when` 的取值必须来自**能力字典**，不是自由文本。
2. **目标能力 ⊇ 请求所需**（逐项校验，而不是"看起来更强"）。
3. **不得涨价**：`估算(目标) > 估算(原模型)` ⇒ **400**。
   "降级"变成"升级"是荒谬的，但极易写出来（尤其当便宜档的 `resolution` 档位不同时）。
   且(§2.4)→ `max_credits` 必须按**降级后**的值重新过一遍。

## 4. 上报契约：`degradations[]`（机器可读的新增块）

现状只有 `warnings[]`（字符串数组）。字符串**无法被机器消费** —— 调用方无法据此判断
"该不该重发/加预算/改需求"，运维也无法按"是否换了供应商"筛选。

在创建/查询响应里补一个**结构化**的块（`warnings[]` 保留给人类，二者是**同一事实的两种表示**，
不产生第二个真源）：

```jsonc
"degradations": [
  {"kind": "param_fallback", "field": "duration", "requested": 7, "effective": 5,
   "direction": "down", "axis": "discrete_tier", "reason": "t2v accepts 5|8",
   "credits_delta": -9},
  {"kind": "model_downgrade", "field": "model", "requested": "doubao-seedance-2-5-260628",
   "effective": "seedance20", "reason": "upstream API has no 2.5 slot",
   "vendor_changed": false, "credits_delta": null},
  {"kind": "param_ignored", "field": "ratio", "requested": "21:9", "effective": null,
   "reason": "wan27 has no 21:9; output follows the first frame instead"}
]
```

| 字段 | 约束 |
| --- | --- |
| `kind` | **固定枚举**：`param_fallback` / `param_clamped` / `param_ignored` / `model_downgrade` / `capability_dropped` |
| `requested` / `effective` | 必须是**实际取值**，`effective: null` 表示"这一项被丢掉了" |
| `credits_delta` | 负 = 更便宜。**拿不到就 `null`，不编数字**（沿用 ADR-004 的口径） |
| `vendor_changed` | 仅 `model_downgrade` 有：**是否换了厂商**（`t2v` 实测底层是 minimax_h3 ⇒ `true`）。这是调用方最需要知道、也最容易漏报的一位 |
| `direction` | 仅回退类有：`down` / `up` / `n/a`。**`up` 必须在 UI/日志里显眼**（它意味着涨价） |

🔴 **`dry_run` 必须完整产出这个块**：它的价值就在于**花钱之前**让调用方看到
"我会替你改什么、因此省/花多少"。做不到这一点的 dry-run 只是"语法检查"。

---

## 5. 与既有纪律的接口（三条不能破）

1. **`max_credits` 仍是提交前置条件**：任何回退/降级之后都要**重算并重过**（§2.4/§3.3）。
   顺序固定：**先定最终取值 → 再估成本 → 再比上限 → 才发上游**。
2. **参考类素材不可静默丢**：降级链**不得**成为"丢掉参考图/视频/音频"的通道。
   降级只允许发生在"目标模型能**完整承接意图**"的前提下。
3. **`provider` 是断言**：`model_map` 与 `fallback_chain` 都在渠道内声明，**跨 provider 一律 400**。
   —— 这两个新配置项给"误路由"开了两扇新门，必须守住。

## 6. 测试矩阵（零消耗；断言"发出去的 body"，不是断言函数返回值）

| # | 用例 | 断言 |
| --- | --- | --- |
| 1 | `duration=6` 对 `t2v`，默认 | 上游收到 `"5"`；`kind=param_fallback,direction=down` |
| 2 | `duration=7` 对 `t2v`，默认 | 上游收到 `"5"`（**不是 `"8"`**）；无涨价 |
| 3 | `duration=7` + `nearest` + 上限够 | 上游收到 `"8"`；`direction=up`；**显式标注涨价** |
| 4 | `duration=7` + `nearest` + 上限只够 5s | **400**，message 指向"向上回退会超上限"；**上游收 0 次** |
| 5 | `duration=2` + `strict` | 400（不回退） |
| 6 | `duration=2` 对 `happyhorse`，默认 `down` | 400（区间下界外且未授权向上） |
| 7 | `ratio=adaptive` 无首帧 + `minimax` | 上游收到 `auto` |
| 8 | `ratio=adaptive` 无首帧 + `t2v` | **400**（不替调用方猜 `16:9`） |
| 9 | 模型名歧义 / 未命中 | 400 + 列出候选/可用名；上游收 0 次 |
| 10 | 能力缺口 + 链上目标可承接 | 降级发生；`kind=model_downgrade`；**降级后估算 ≤ 原估算** |
| 11 | 能力缺口 + 链上无目标 | 400，说明"哪个能力、哪个槽位能满足" |
| 12 | 上游 5xx / 429 | **不降级**；502 / 429（可用性不是能力） |
| 13 | `fallback_chain` 指向别的 provider | 400 |
| 14 | 降级目标是更弱能力（缺首尾帧） | 400（§3.2 第 4 条） |
