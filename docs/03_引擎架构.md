## 0. 一句话

把**任意视频异步接口**适配为**火山方舟 Seedance 视频生成协议**：
调用方只改 Base URL 与 API Key，即可把既有 Seedance 集成切到我们的上游。

## 1. 架构决策（本次确认）

| # | 决策 | 内容 |
| --- | --- | --- |
| **D1** | **渠道配置来源** | 与 image-adapter 完全一致：**11 个 HTTP 头**驱动，服务端不持有渠道/模型/计费知识 |
| **D2** | **翻译脚本写死在项目** | 只接受 `X-Script-Ref` 命名引用；**内联脚本（`X-Script`/`X-Script-64`）被拒绝** |
| **D3** | **引擎移植 image-adapter** | 脚本 + AST 沙箱 + 相位（create/query/cancel）+ `ctx` API + 任务状态存储 |
| **D4** | **首批上游** | aivideomaker **官方 API 线**（`key` 头 + `/api/v1/*`，8 个模型） |
| **D5** | **本文取代 playbook §10** | 见 §1.5 |

### 1.1 职责边界

| | 控制面（New API） | 数据面（本服务） |
| --- | --- | --- |
| 职责 | 渠道 / 模型 / 计费 / 路由 | 协议转换、任务编排、持久化、可观测 |
| 配置来源 | 渠道配置界面 → **HTTP 头透传** | 无配置文件，全部由请求头驱动 |
| 状态 | 持久化 | 任务表（**必须持久化**，见 §6.2） |

推论：**一个渠道 = 一个上游端点 + 一个脚本 ref**。同厂商不同能力各建一个渠道，
天然复用 New API 的负载均衡与故障切换。

### 1.2 为什么是"脚本写死"而不是"调用方内联脚本"

内联脚本在 image-adapter 里是"简单上游字段映射的草稿纸"。但本项目的第一等公民是
**降级报告**（`adapter-playbook.md` §3.2）——它要求翻译逻辑承担语义判断（丢掉某项会不会改变
"用户想要什么"）。这种逻辑**必须经过 review、可追溯、随镜像发版**，
不能由调用方在请求头里现场投喂。

- `ALLOW_INLINE_SCRIPT` **默认 `false`**（与 image-adapter **相反**，其默认是 `true`）；
- 带 `X-Script` / `X-Script-64` 的请求 → `channel_config_error`（400），
  消息里点名"请改用 `X-Script-Ref`"；
- 生产同时开 `SCRIPT_PIN_MANIFEST_DIGESTS=true`，把 ref 内容钉在 manifest 摘要上。

> 11 个头的**名字与语义全部不变**，只是其中两个来源被策略关闭。契约表仍由
> `adapter/main.py::channel_contract` 用 `Header()` 声明，`/docs` 可直接试调，不会与实现漂移。

### 1.3 引擎为什么能移植

image-adapter 的引擎骨架（沙箱 / 编译缓存 / scriptstore 链 / 传输层 / 错误体系 / 中间件 /
追踪）**不含任何图片语义**，是通用执行引擎。移植时只改三处：

1. **出口形态**：OpenAI 错误信封 → **Seedance 错误信封**（§10）；
2. **相位集**：`request/response/poll_*` → `create_*/query_*/cancel_*`（§5）；
3. **`ctx` 能力**：去掉图片专属（`image_ref` / `imageops` / `fanout` / `caps`），
   加入任务上下文（`ctx.task`）与素材转存（`ctx.upload_asset`）。

### 1.4 不复用的模块（避免"看起来能用"的死代码）

`api/images.py`、`api/image_edits.py`、`api/frontdoor.py`、`api/chat.py`、`api/responses.py`、
`utils/imageops.py`、`ctxapi/image_ref.py`、`utils/fanout.py`、`ctxapi/mapping.py`、
`ctxapi/caps.py`、`capabilities.py`、`stages.py` / `stage_spec.py`（级联）。

> 视频没有"多图编辑 / 多轮对话 / 尺寸归一化 / 图层拆分 / 多级级联"这些语义。

### 1.5 为什么取代 playbook §10

| | playbook §10（原） | 本文（现） |
| --- | --- | --- |
| 分层 | `app.py` / `translate.py` / `store.py` / `client.py` / `queue.py` / `media.py` / `callback.py` | 引擎（共享）+ `script_store/<provider>/video@v1.py`（每上游一份） |
| 接第二个上游 | 复制一套目录 | 加一个脚本 + 一段渠道配置 |
| 测试重心 | `translate.py` | 同一位置，只是路径变成脚本文件（`importlib` 直接加载仍成立） |

**保留的是 playbook 的全部结论**（降维矩阵、判定准则、计费护栏、14 项测试），
**改的只是它们的落点**：`translate.py` → 脚本；`store.py`／`queue.py`／`callback.py`／`media.py`
→ 引擎模块（一次实现，所有上游共享）。

## 2. 前门：四条路由（路由固定 + `model = provider/model` 区分上游）

### 2.1 路由表

严格逐字实现 `seedance-api-reference.md` §2 的四个端点，**路径不做任何改动**：

| 方法 | 路径 | 响应 |
| --- | --- | --- |
| POST | `/api/v3/contents/generations/tasks` | `{"id": "cgt-YYYYMMDDHHMMSS-xxxxx"}` —— **逐键只有 id**（没有 status、**也没有上报块**） |
| GET | `/api/v3/contents/generations/tasks/{id}` | **原生任务对象**（六态；**逐键等于原生字段集**，不含 `model`、不含任何诊断块） |
| GET | `/api/v3/contents/generations/tasks` | `{"items": [...], "total": N}` |
| DELETE | `/api/v3/contents/generations/tasks/{id}` | `queued` → 取消；终态 → 删除记录 |
| GET | `/healthz` | 存活（全服务一份）；`?deep=1` 额外查上游余额 |

⇒ **一个 `base_url` 服务所有上游**；多上游靠 `model` 字段区分（§2.3）。

### 2.2 路径形态：只有火山原生一族

**路径主体只有一条**：`/api/v3/contents/generations/*`，且**逐字等于原生**。

不做 `/api/plan/v3`（Agent Plan 企业版）与 `/api/v1`（LAS 算子）的前缀兼容 ——
后两者是**同一逻辑 API 的另两种投放形态**，不是本项目的接入目标。

> 多前缀真有必要时，属**部署层（反向代理）**职责。不放进应用的理由：它解决的是部署形态问题
> 而非协议问题，一旦进应用就变成需要长期维护的路由分支。

### 2.3 多上游区分：`model = provider/model`

**唯一的多上游区分手段**，路径保持固定。

```
"model": "aivideomaker/doubao-seedance-2-5-260628"
          └── provider ──┘ └──────── 模型 ────────┘
```

**为什么这个切法天然成立**：控制面（New API）本来就**按 `model` 名路由到渠道**。
把 provider 放进 `model`，等于把"选哪个上游"交回控制面，数据面只做解析与校验 ——
**不需要在数据面维护任何渠道注册表**（D1 不破）。

| 议题 | 规则 |
| --- | --- |
| 语法 | `<provider>/<model>`；`provider` 卡 `^[a-z0-9][a-z0-9_-]{0,62}$`；**只允许一个 `/`**（模型名本身不含 `/`） |
| `provider` 的角色 | **断言 + 命名空间**，**不是凭证来源**：必须与渠道声明的 `X-Channel-Options.provider` 一致；**不一致 → 400 `InvalidParameter`** |
| 为什么要这条断言 | 专门杜绝"`model` 写错/漏改 → 静默落到别的上游 → **直接付费**"。这是模型名路由最大的风险面 |
| 凭证与上游地址 | 仍全部来自请求头（D1 不变）；`provider` 不参与取凭证 |
| 裸模型名（不含 `/`） | 调用方沿用官方写法时，落到**渠道声明的默认 provider**；**渠道未声明 provider ⇒ 400，绝不猜** |
| 与脚本模型映射的关系 | `provider` 选上游；`<model>` 段**默认逐字透传**，需要翻译时由渠道的 `model_map`（§4.2）映射 —— **精确优先，键可含唯一元字符 `*`，且不排序、不取最长** —— 脚本体里**没有**也不该有名字映射表（§5.3"模型名"一节） |
| 任务命名空间 | 任务键含 `provider`；**跨 provider 读任务必须 404** |
| 幂等指纹 | 含 `provider` 与完整 `model` 串 |
| 响应回显 | 🔴 **不回显**（2026-09-16 起）：上游模型名很乱，回显它没有信息增量。调用方要"我请求的 vs 实际生效的"请读 `dry-run` 或 logfire 的 `task.effective.*`（`seedance-api-reference.md` §0.0） |
| 未知 provider | 400，message 只点出**本渠道声明的** provider，不泄露全局清单 |

**查询 / 取消怎么办（`model` 方案唯一的硬约束）**：`GET`/`DELETE` 的路径与请求体里**都没有 `model`**，
⇒ 渠道身份有两个来源，**两个都要用**：

1. **任务记录**（创建时已落库）→ 提供 `provider`，用于命名空间校验与响应回显；
2. **请求头**（与创建同一渠道，§6.3 方案 A）→ 提供上游地址与凭证。

两者不一致 ⇒ **404**（不泄露"该任务属于别的 provider"）。
这是"路由固定"付出的唯一代价，必须在测试里钉住一致性 ——
否则会出现"创建时走 A、查询时按记录查 B"的错位。

#### 两个轴：模型出品方 ≠ API 供给方（"来源"到底用哪个字段区分）

这是最容易建模错的一处：**模型名里出现的品牌，往往不是 API 的提供方**。

| 轴 | 回答的问题 | 例子 | 进不进路由 |
| --- | --- | --- | --- |
| **模型出品方**（model owner） | 这个模型是谁训练的 | DeepSeek、Qwen、Doubao、MiniMax | ❌ **不进路由** |
| **API 供给方**（provider） | **这次请求发给谁** | DeepSeek 官方、阿里百炼、火山方舟、aivideomaker | ✅ **进路由** |

同一个 `deepseek-v3` 至少有三家供给方，**端点、凭证、计费、限流、能力全不同**：

```
"model": "deepseek-official/deepseek-v3"     ← DeepSeek 自家 API
"model": "aliyun-bailian/deepseek-v3"        ← 阿里百炼托管的 DeepSeek
"model": "volcengine-ark/deepseek-v3"        ← 火山方舟托管的 DeepSeek
```

⇒ **`provider` 段永远是「API 供给方」，不是「模型出品方」。**

「DeepSeek 由谁提供」这个问题的答案写在 `provider` 段里，**不是**写 `deepseek/...` ——
`deepseek/` 这种写法会让"官方线"和"阿里托管的同一模型"**撞在同一个 token 上**，
再叠加"值必须等于渠道声明"的断言，结果就是**合法的请求被 400 或被误路由**。

**模型出品方放哪？** 不进 `model` 前缀，也不加进响应体（避免偏离原生契约）。
它已经隐含在被托管的模型名里（`deepseek-v3`）；归属与分账若真需要，
由控制面自己的「模型名 → 归属/定价」映射处理 —— 那是控制面的既有职责，
不需要数据面为此多传一个字段。

#### 为什么字段名取 `provider`，而不是 `biz` 或 `vendor`

| 理由 | 说明 |
| --- | --- |
| **与生态惯例同形** | `<provider>/<model>` 是既成事实（OpenRouter、LiteLLM）。注意它们语义上指的也是**供给方 / 集成**，不是模型出品方 —— 与本项目一致 |
| **语义对轴** | `biz` 是"业务"，在网关语境里天然读作"哪个业务方 / 租户" —— 那是**调用方**的轴。两个轴混进一个字段，做多租户时必然打架 |
| **`vendor` 会骗人（已否决）** | `vendor` 读作"模型厂商"。而在 `aliyun-bailian/deepseek-v3` 里，阿里并不是 DeepSeek 的 vendor，而是**供给方** —— 用 `vendor` 命名会让每个接入方多问一次"这里填模型厂商还是 API 提供方？" |
| **与 D1 的措辞一致** | §4 头契约讲的一直是"上游地址 / 凭证 / 脚本 ref"，主语就是**供给方**，`provider` 正好对齐 |

⚠️ **仍然必须满足的约束**：`provider` 与渠道 **1:1**。同一供给方有多条接入线时
（例如 aivideomaker **官方 API 线** vs **网页端内部接口**），token 取 `aivideomaker-official` /
`aivideomaker-web` —— **字段名不变，值可以更长**。错配时"值必须等于渠道声明的 provider"
这条断言会直接 400，不会静默落到另一条线。

> **命名演进（三次，留痕以免重走）**：`biz`（路径段方案，已退役）→ `vendor`（已否决，
> 理由见上表第 3 行）→ **`provider`（现行）**。

> `{biz}` 这个词**已随路径段方案一并退役**，只保留在 §15 的作废记录里，
> 不再出现在任何有效定义中（避免两套术语并存）。

> **备选（未采纳，保留记录）**：在路径前加 `{biz}` 段
> （`/{biz}/api/v3/contents/generations/*`，一个渠道一个 `base_url`）。
> 优点是**路径即命名空间**、与 New API"一渠道一上游"模型严丝合缝；
> 代价是**路径偏离原生**、且调用方要按渠道改 `base_url`、多前缀需长期维护。
> 现选择"路径零偏差 + `model` 区分"。

### 2.4 任务 ID 形状

`cgt-<YYYYMMDDHHMMSS>-<5~8 位随机>`，模仿原厂，使调用方既有的正则校验与日志关联不变。
**不使用上游的 id 作为对外 id**（不同上游 id 空间会撞，且形状不同）。

### 2.5 DELETE 的两种语义

| 任务状态 | 行为 |
| --- | --- |
| `queued` | → `cancelled`（**唯一可取消的态**）；成功后**不触发回调** |
| 终态（`succeeded`/`failed`/`expired`/`cancelled`） | 删除本地记录 |
| `running` | 拒绝（400 `InvalidParameter`，message 说明"仅 queued 可取消"）—— 上游若支持强杀，由脚本的 `cancel_*` 相位决定，但对外状态语义以本文为准 |

⚠️ **上游没有取消端点时（脚本不声明 `cancel_*` 相位），`queued` 的 `DELETE` 也是 400**
（`ADR-014`）：这不是"引擎能力不足"，而是**不允许伪造 `cancelled`** —— 上游任务会继续跑
（继续计费），而本地一旦置为终态，就会提前释放并发槽位、并在响应里给出一个假的状态。
终态任务的 `DELETE`（删本地记录）**不受影响**。

## 3. 请求归一化（前门职责，**先于脚本**）

以下四项必须在路由层完成，脚本侧永远看不到未归一化的输入。

### 3.1 弱校验后缀必须先剥离

调用方可能用官方的**弱校验模式**把参数内联在提示词尾部（`seedance-api-reference.md` §9）：

```
"小猫打哈欠 --rs 720p --rt 16:9 --dur 5 --seed 11 --cf false --wm true"
```

入口必须**先解析并剥离**这组后缀（简称与全称都要认：`--rs/--resolution`、`--rt/--ratio`、
`--dur/--duration`、`--seed`、`--cf/--camerafixed`、`--wm/--watermark`），合并进结构化字段，
**再**把干净文本交给脚本。

- **优先级**：显式结构化字段 **>** 内联后缀（与官方"常规方式优先"一致）。
- **理由**：否则上游收到一段带 `--rs 720p` 的污染提示词，画面里可能真的出现这些文字。

### 3.2 `content[]` 归一化

| 项 | 规则 |
| --- | --- |
| `role` 的位置 | **两种都收**（content 项顶层 / `image_url` 对象内，后者是第三方镜像的 divergent 写法）；**出口一律按官方顶层产出** |
| 首尾帧隐式语义 | 2 张无 `role` 的 `image_url` + 有文本 ⇒ 归一化成显式 `first_frame` / `last_frame`（**顺序即语义**） |
| 多个 `text` 项 | 按数组顺序用换行拼接为单条 prompt（**不要取最后一条**） |
| `@图像n` / `@视频n` | 位置引用。若脚本裁剪/重排了 media 数组，**必须同步重写提示词里的编号**，否则"参考@视频2"指向错素材 |
| `frames` 与 `duration` | 二选一，`frames` 优先（`seedance-api-reference.md` §3.1）；`frames` 需满足 `25+4n` |

### 3.3 降级报告是一等公民

响应里必须能让调用方看见"哪些能力被丢掉了"：

- `warnings[]`：吸附、换算、弱化（如 `seedance20` 收到 1080p 降到 720）；
- `unsupported[]`：上游没有对应能力的字段（`omni_reference_task_type`、`output_format`、
  `draft`、`service_tier`、`priority`、`return_last_frame`、`tools`、`safety_identifier` …）。

### 3.4 参考类素材一律不能静默丢

判定准则（`adapter-playbook.md` §3.2）：**丢掉这一项，会不会改变"用户想要什么"？**

- **会** → 返回 **400 `InvalidParameter`**，message 指明是哪一个 `content[i]`；
- **不会，只是画质弱化** → 保留、降级、写入 `warnings[]`。

⇒ `reference_image` / `reference_video` / `reference_audio` / `{draft_task}` 缺失对应能力时必 400；
只有 `last_frame` 在单图上游上可降（取首帧 + warning）。

## 4. 渠道契约（11 个 HTTP 头）

| 头 | 必填 | 说明 |
| --- | --- | --- |
| `X-Upstream-Url` | 是 | 上游完整端点 |
| `X-Script` | 三选一 | 内联源码 —— **本服务拒绝**（D2） |
| `X-Script-64` | 三选一 | 源码 base64 —— **本服务拒绝**（D2） |
| `X-Script-Ref` | 三选一 | 命名引用，如 `aivideomaker/video@v1` —— **唯一接受的脚本来源** |
| `Authorization` | 否 | **上游厂商**凭证，原样透传，不用于本服务鉴权 |
| `X-Adapter-Key` | 是 | 本服务准入密钥 |
| `X-Upstream-Method` | 否 | 默认 `POST` |
| `X-Auth-Emit` | 否 | 凭证位置非标准时用，如 `header:key:`（aivideomaker 用裸 `key` 头，无 `Bearer` 前缀） |
| `X-Async` | 否 | **本服务不再需要**（§4.1） |
| `X-Script-Sha256` | 否 | 完整性锁定 |
| `X-Channel-Options` | 否 | JSON 对象，脚本内通过 `ctx.options` 读取 |

### 4.1 `X-Async` 为什么消失

image-adapter 的 `X-Async` 是"把异步上游**转成同步响应**"的开关（内部跑阻塞轮询）。
本服务的**规范格式本身就是异步的**（创建返回 id、调用方轮询），所以"异步"是协议属性、
不是渠道属性。副作用是整条 `_run_poll_loop` / `PollTimeoutError` 路径被删除，
服务端不再持有长连接。

### 4.2 `X-Channel-Options` 的已定义键

| 键 | 作用 |
| --- | --- |
| `provider` | **本渠道声明的 provider**（§2.3）：`model` 里的 provider 段必须与它一致，否则 400；也是"裸模型名"的默认落点 |
| `model_map` | 调用方模型名 → 上游槽位名的映射表（如 `{"doubao-seedance-2-0-260128": "seedance20"}`）。**精确优先**；键里含 `*` 即为通配模式（`*` 是唯一元字符、大小写敏感、`?`/`[]` 字面量），如 `{"doubao-seedance-*": "seedance20"}`；**`{"*": "t2v"}` = 本渠道只跑 t2v，连合法槽位名也改写**（通配在"名字本身就是槽位名"之**前**）。两条通配同时命中 ⇒ `channel_config_error`（不排序、不取最长）。旧名 `upstream_model_map`（本文档曾登记、但从未实现）作为**别名**仍接受；两个都写且不同 ⇒ `channel_config_error`。键是**调用方写什么**，值是**上游认什么**（必须是槽位名）；值非法/重复键均拒绝。命中记 `effective.model_map_applied` + `effective.model_map_pattern` |
| `max_credits` | **支出上限（渠道级天花板）**，见 §9.1。**必填** —— 上游没有计费前闸门 |
| `credit_table` | 给**动态计价模型**补每秒费率（如 `{"seedance20": 12}`），让它恢复可估，见 §9.1 |
| `allow_unpriced` | 显式接受"成本不可在提交前验证"（算不出成本时的第二条出路），见 §9.1 |
| `max_concurrency` | 该渠道同时在上游的任务数上限，见 §7 |
| `rehost` | 产物是否转存到自有存储（**默认 false**），见 §8.2 |
| `credits_per_token` | `usage` 折算倍率，默认 1（1 积分 = 1 token 当量），见 §8.2 |
| `webhook_url` | 上游侧的**内部**回调地址；只认渠道配的，**绝不透传**调用方的 `callback_url` |

⚠️ **脚本自有的键**（引擎只负责把它们原样交给 `ctx.options`，**不解释**）：脚本可以定义
自己的选项，命名与语义由该脚本的文档负责。已经有的三个（`senseaudio/video@v1`）：

| 键 | 作用 | 默认 |
| --- | --- | --- |
| `status_binding` | 查询的身份绑定形态：`credential` = **不带参数**、身份来自 API key、本层**验明返回记录的 `task_id` 是不是本任务的**（不一致 ⇒ 400，`ADR-016`）／`task_id` = 带参数、由上游过滤。取其它值 ⇒ `channel_config_error` | `credential`（跟实测） |
| `query_id_param` | **只在 `status_binding=task_id` 时生效**：查询参数名（文档写 `id`）。只允许 `[A-Za-z_][A-Za-z0-9_]*` | `id` |
| `retry_after_seconds` | 上游**没说**等多久、而出口又是 429 时的退避值（**上游给了就优先用上游的**） | 空 = 不带 `Retry-After` |

> ⚠️ 曾经有过 `generate_audio_field`（`flat` / `provider_specific`），**2026-09-17 已撤除**：
> 实测确认**上游只认嵌套** `provider_specific.generate_audio`（扁平是火山原生独有的形态），
> 于是形态固定、不再需要开关 —— 已知正确形态后还留一个能改错的旋钮，只会留出
> "配错了就没声音"的静默空间。渠道若仍写着这个键，会被**静默忽略**（脚本不认得的键本来就不看），
> 而结果正好是正确的那一种。

> 🔴 `status_binding=credential` 的连带要求：**同一把钥匙同一时间只该有一个在跑任务**
> （上游只能回答"当前那一个"）⇒ 该渠道应配 `max_concurrency: 1`。
> 引擎的闸门键正好是 `provider:凭证指纹`，与上游这层语义同轴 —— 配了之后就不会有
> "旧任务被顶掉、查询只能 400"的情形。

> 这三个键都只影响"发出去的请求形状/退避值"，都**不是**把上游知识写进引擎 ——
> 脚本不认得的键会被静默忽略（这是既有语义），所以加一个键不会破坏另一个上游的渠道配置。

⚠️ `model`（渠道级"钉住槽位"）**2026-09-16 已撤除**（`ADR-012`）：它只做一致性断言、不承担转换。遗留该键 ⇒ `channel_config_error`（**响亮失败**，不静默忽略，且值合法时也照拒）；"让这个渠道只跑某个槽位"改用通配 `{"*": "<槽位>"}` —— 注意它**改写**模型值而不是拦下请求 |

## 5. 脚本契约

### 5.1 相位集

| 相位 | 触发路由 | 必需 | 输入 → 输出 |
| --- | --- | --- | --- |
| `create_request` | POST | 是 | 规范体 → 上游创建请求体 |
| `create_response` | POST | 是 | 上游创建响应 → `{"task_id": …}` |
| `query_request` | GET | 是 | `ctx.task` → 查询请求计划（`ctx.emit(url=…)`） |
| `query_response` | GET | 是 | 上游查询响应 → 规范化片段 |
| `cancel_request` | DELETE | 否 | `ctx.task` → 取消请求计划 |
| `cancel_response` | DELETE | 否 | 上游取消响应 → `{"status": "cancelled"}` |
| `create_error` / `query_error` / `cancel_error` | 对应路由**非 2xx** 时 | 否 | 上游错误体 + `ctx.upstream_error` → `ctx.fail(…)` 抛出精确错误，**或正常返回 = 不拦**（`ADR-015`） |

**错误相位（`ADR-015`）**：非 2xx 的响应体**到不了** `*_response`（引擎在 `raise_for_status`
处就抛了），所以想看厂商业务码（如 `400015` = 并发已满）只能靠这个可选钩子。
三条约束：① **可选**（不声明即老行为，零回归）；② **不拦就算**（回落通用映射，
"认不出的码"由脚本决定不拦）；③ **不许用它掩盖上游错误**（相位自己崩了只记日志 + 回落）。
`ctx.upstream_error` 只在错误相位里有值：`{status, retry_after, headers, phase}`。

`query_response` 的规范化片段形状：

```json
{"status": "running|succeeded|failed|expired|cancelled",
 "video_url": "…" | null, "last_frame_url": "…" | null,
 "usage": {"completion_tokens": 0, "total_tokens": 0},
 "width": …, "height": …, "duration": …, "frames": …, "framespersecond": …,
 "seed": …, "resolution": "…", "ratio": "…",
 "error": {"code": "…", "message": "…"} | null,
 "warnings": []}
```

- 可选相位须用模块级 `PHASES` 声明，否则 `channel_config_error`；
- 脚本**只做翻译**：不碰 socket、不读环境变量（`translate` 层纯函数化，env 显式注入）、
  不知道自己在哪条路由后面。

### 5.2 ctx API

延续：`ctx.options` / `ctx.upstream_url` / `ctx.request_id` / `ctx.key` / `ctx.emit(...)` /
`ctx.fail(msg, code=…, param=…, status=…)` / `ctx.logfire` / `ctx.encode_b64` / `ctx.decode_b64` /
`ctx.sniff_mime`。

### 5.3 首个脚本：`script_store/aivideomaker/video@v1.py`

上游 = aivideomaker **官方 API 线**。**上游契约唯一真源**是
`docs/upstreams/aivideomaker-official-api.md`（含 8 个模型的字段表、计费公式、限流）。

| 本服务路由 | 上游端点 |
| --- | --- |
| POST 创建 | `POST /api/v1/generate/{model}` —— **路径参数每请求变，由脚本展开 `{model}`** |
| GET 查询 | `GET /api/v1/tasks/{id}`（用**详情**而非 `/status`：后者不带产物地址） |
| DELETE 取消 | `PUT /api/v1/tasks/{id}/cancel` ⚠️ **必须 PUT**（POST/DELETE 均 405）；**仅 `SUBMITTED` 可取消** |

**状态映射**：`SUBMITTED`→`queued`，`PROGRESS`→`running`，`COMPLETED`→`succeeded`，
`FAILED`→`failed`，`CANCEL`→`cancelled`（上游无 `expired`，由看门狗兜底，§6.5）。
⇒ 脚本产出的状态**只会是原生六态**；引擎另有一道兜底：越界值一律收敛为 `running`
（非终态）并上报 `task.status.unnormalized=true`（`seedance-api-reference.md` §4.3）。

#### 模型名：**透传**，映射由渠道配置（2026-09-16 起）

本脚本**不改模型值**。调用方写什么就发 `POST /api/v1/generate/{什么}`，合法值 = 上游 8 个槽位名。
需要"原生 ID → 槽位名"时由渠道给 `model_map`（§4.2）。**不要**在脚本体里重建名字映射表：

| | 旧实现（已删） | 现在 |
| --- | --- | --- |
| 机制 | 模块级正则表 `_MODEL_PATTERNS`，**顺序敏感** | 渠道 `model_map`：**精确优先**，键可含**唯一**元字符 `*`（通配优先于"名字本身就是槽位名"），**两条同时命中即报错** |
| 未知名 | 命中不了才 400；但 `seedance*` 一律命中 | 400，并列出合法槽位 + 渠道已配的键 |
| 命中是否可见 | **不可见**（连 `warnings[]` 都没有） | `effective.model_map_applied` + `effective.model_map_pattern`（**命中的模式**）+ logfire |
| 实测代价 | 5 个代次的原生 ID 全落 `seedance20`，账单是 `t2v` 的 **7.3 倍**（110 vs 15 积分） | 不映射就不会误路由；要映射就显式配置 |

#### 旧实现在官方文档到手后被修正的 6 处

`videos/src/ark_compat/translate.py` 是针对**网页线**观测写的，其中若干处对官方线只是**猜测**
（源码里自己标了 "unverified"）。拿到官方文档后逐条核对，以下都要改（详见上游文档 §7）：

| # | 旧做法 | 修正 |
| --- | --- | --- |
| 1 | 一张**全局**时长档位表套所有模型 | 改成**按模型**：t2v/i2v 只有 `5/8`；\_v3 是 `5/10/15/20`；seedance20 `4–15`、minimax `5–20`、happyhorse `3–15` 是**连续区间** ⇒ 直接钳制，**不再"就近吸附"**（吸附正是跨进更贵档的入口） |
| 2 | `seedance20` 发 `lastFrameImage` / `referenceImages` / `referenceVideoUrl`，均标"未验证"却照发 + 告警 | 真字段是 `image` / `video` / `audio`，**各单个**。尾帧 → 取首帧 + warning；参考图 >1 张 → **400** |
| 3 | 把 `X-Max-Credits` 当上游的计费前闸门 | ⚠️ 文档**没有**该头（见 §15 第 11 条）⇒ 上限改为**本层本地估算**拦截 |
| 4 | 未知模型名**兜底落 `seedance20`** | **400 + 可用清单**。兜底落默认值 = 写错一个字母就提交到别的上游并**直接计费** |
| 5 | `adaptive` 直接丢弃 | minimax 显式支持 `auto` ⇒ 原样映射；seedance20 的 `ratio` **必填**，`adaptive` 告警后落 16:9；其余按允许集吸附 |
| 6 | `happyhorse`/`wan27` 的 `duration` 发成 string | 两者都是 **number**；`wan27` 的 `duration` 才是 string。`i2v*` **没有比例字段**，发了会 `INVALID_PAYLOAD` |

#### 其余与旧实现的差异（能力面）

- **未知模型名绝不兜底**（同 #4，是本脚本最重要的一条）；
- **支出上限是提交前置条件**：拿不到 `max_credits` → 400；7 个模型按官方公式**本地估算**，
  估算值 > 上限 → 400；`seedance20` 动态计价无法估算 ⇒ **如实告警**而不是假装守住；
- **引擎兑现的字段不进 `unsupported[]`**：`callback_url` / `execution_expires_after`
  由引擎兑现，报成"上游不支持"会让调用方以为能力缺失；
- **`webhookUrl` 只来自渠道选项**（内部回调地址），**绝不透传调用方的 `callback_url`** ——
  否则我们的回调重试语义会被上游的 webhook 语义顶掉；
- **调用方的错与运维的错分开报**：调用方传错 `model`/`ratio` → 400 `InvalidParameter`；
  渠道头配错 → `channel_config_error`。

### 5.4 第二个脚本：`script_store/senseaudio/video@v1.py`（2026-09-17）

**状态映射**：`pending`→`queued`，`processing`→`running`，`completed`→`succeeded`，
`failed`→`failed`（上游无 `cancelled`/`expired`：前者因为无取消端点，后者由看门狗兜底）。

这个上游把四类**会静默出错**的地方暴露得比首个上游清楚，逐条对应脚本里的决定：

| # | 事实 | 决定 |
| --- | --- | --- |
| 1 | `watermark` 上游默认 **`true`**、原生默认 `false`；`generate_audio` 上游藏在 `provider_specific` 且未写默认（原生 2.x 默认 `true`） | **两个字段一律显式发送** —— 省略任一个 = 把"实际生效值"交给别人的默认值，而响应体已不再是降级告知通道（`ADR-011`） |
| 2 | `content[]` 三处形状不同：图片 URL 是**平铺** `url`、类型名是 `image`（非 `image_url`）、`reference_image` 要改写成 `reference` | 逐项改写类型名与字段位置；**声明式不改语义** |
| 3 | 首尾帧模式与参考素材模式**互斥**，且仅音频不合法 | 混用/仅音频 ⇒ **400**（丢掉任一侧都改变了"用户想要什么"） |
| 4 | 上游**没有任何计费 / 用量字段** | `usage` 恒 `null`（不编 token 数）；`max_credits` 仍是提交前置，成本只能靠渠道 `credit_table` 恢复可估，否则要 `allow_unpriced` |

另有两条**只在实现里才看得见**的纪律：

- 🔴 **媒体顺序一字不动**（`_split_content` 单次遍历 → `build_content` 原序产出）：
  Seedance 的 `@图像1/@视频1` 编号按媒体**出现顺序**算，按类型分组重排会让编号指向别的素材，
  且几乎无法归因。测试里专门用"图、视频、图"的交错顺序钉住它。
- 🔴 **"上游缺这个能力"与"请求写错了"分开报**：认不出的 `content[].type`、
  以及**认得类型却没有 URL** 的项 ⇒ 400 `InvalidParameter`（请求错误），
  **不是** `unsupported[]`（能力缺口）。首个脚本把这两种混在一起（都进 `unsupported[]`），
  本脚本刻意分开 —— 因为它们指向的修复动作完全不同。

⚠️ **一处引擎侧的连带修正**：`adapter/tasks.py::delete()` 原先在脚本未声明 `cancel_request`
时会**静默**把本地任务置为 `cancelled` 并释放并发槽位（上游继续跑、继续计费）。
现在改为 400 响亮失败，见 `ADR-014`。

```json
 "script_ref": "aivideomaker/video@v1", "model": "doubao-seedance-2-5-260628",
 "credential_id": "hmac-sha256:9f2c…", "status": "running",
 "created_at": 1789000000, "updated_at": 1789000012, "expires_at": 1789604800,
 "request": {…规范创建体…}, "callback_url": "…", "tokens_charged": null}
```

**`credential_id` 不是凭证本身**（见 §6.3）：它是**创建时那把 API Key 的指纹**，
用来回答"这个任务当初是用哪把钥匙建的"。`upstream_task_id` + `credential_id` 一起，
构成"日后回查上游"的全部所需 —— 而两者都不含秘密。

### 6.2 🔴 任务表**必须持久化**（对既有认知的一处修正）

`adapter-playbook.md` §2 明确：一旦适配层要合成任务，就必须承担任务持久化，
**至少保留到 `GET` 的 7 天窗口，且进程重启不能丢**。

⚠️ 因此 **image-adapter 那套"Redis 缺失则进程内 dict 降级"不能照搬**：
那个降级对图片是"丢一轮对话上下文"级的损失，对本项目是**直接违反契约**
（重启后 `GET` 404，而调用方以为任务还在跑）。

⇒ 设计：**redis 是唯一的生产后端**（`start()` 在 lifespan 里做启动探测，连不上直接失败）；
**进程内 dict 只允许作为单实例开发模式的显式开关**（`TASK_STORE=memory` + 启动时打 warning），
不允许作为隐式降级。

🔴 **sqlite 后端已移除**（2026-09-13）。它曾经是"无 Redis 部署的合规降级"（落盘、重启不丢），
但它**是单机存储** —— 而任务与配额都属于"跨副本共享"的语义（§7.1 的限流桶按出口 IP 共享、
任务表要能被任一副本读到）。多副本下它直接失效，留着等于长期维护一条**注定不可用**的部署路径；
容器里它还要持久卷 + 单 worker + 优雅停机三件套。收敛掉它，部署形态只剩一种。

### 6.3 渠道上下文从哪来 + 任务必须与凭证绑定

#### (a) 上下文来源：三个动作都带头

查询/取消需要知道"用哪个上游、哪个脚本、什么凭证"，而这些在 D1 下是**请求头**、服务端无状态。

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| **A. 查询/取消也带同样的头**（推荐） | 调用方的 SDK `base_url` 指向本服务、`api_key` 即渠道凭证 ⇒ 三个动作天然都带头；服务端只存上游 id | 与 image-adapter 完全一致、服务端无状态；⚠️ 必须写进接入文档 |
| B. 创建时把 URL/ref/凭证快照进任务表 | 查询时无需带头 | **凭证落盘**（违反"密钥不入库"）；凭证轮换后旧任务查不动 |
| C. 单渠道部署，配置读环境变量 | 最简单 | 与 D1 冲突 |

**推荐 A**，并把这条写进 README 的接入示例（否则接入方会以为"创建完就什么都不用带了"）。

#### (b) 🔴 但"都带头"还不够：任务必须与**那一把**凭证绑定

异步上游有个同步调用没有的问题：**任务要在几天后回查，而回查时带哪把钥匙并不确定**。
两个事实都来自上游契约本身：

1. **接口要求**：`GET /api/v1/tasks/{id}` 必须带 `key` 请求头；
2. **可见性也是按钥匙分的**：上游的 `GET /api/v1/tasks` 只返回**当前 API Key 名下**的任务
   —— 上游侧的任务归属就是"那把钥匙"，既不是我们的 `provider`，也不是我们的渠道。

⇒ 于是"认出是哪把钥匙"这件事必须由我们自己做：

| 议题 | 做法 |
| --- | --- |
| 记住什么 | `task:<local_id>` 里记 **`credential_id` = 创建时那把 Key 的指纹** + `upstream_task_id`。**永不落盘明文 Key** |
| 查询/取消时 | 取本次请求头里的 Key → 算指纹 → **与记录不符 ⇒ 本地直接 404**，**根本不发上游请求** |
| 为什么必须本地拦 | 放行到上游就是用**错的钥匙**去查，返回的 404/空**无法区分"任务真没了"与"钥匙不对"**；更糟的是把跨凭证隔离交给了别人的实现去兜 |
| 指纹怎么算 | `HMAC-SHA256(TASK_KEY_FINGERPRINT_SECRET, key)`。要 HMAC 而非裸 sha256：API Key 是低熵可枚举空间，裸哈希可离线爆破。缺 secret 时退化为 `sha256(key)`，同时记录 `credential_algo` 并在启动打 warning（**不静默**） |
| 钥匙轮换 | 轮换后**旧任务只能用旧钥匙查** —— 这是上游的归属语义，不是本项目的缺陷。接入文档要写明；**不要**为了"让旧任务还能查"把 Key 快照进库（那正是方案 B 被否掉的理由，且轮换后同样失效） |

> 首个脚本（`aivideomaker/video@v1.py`）的 `query_request` / `cancel_request` **只拼 URL 与方法**，
> 凭证由引擎作为请求头注入 —— 脚本看不到、也不该看到 Key。

### 6.4 惰性轮询

默认**没有后台轮询器**：每次 `GET /tasks/{id}` = 一次上游查询调用
（`query_request` → 上游 → `query_response` → 规范化 → 更新任务表）。
好处：无长连接、无轮询风暴、成本随调用量线性。

> ⚠️ 惰性轮询同样受 (b) 约束：查询用的钥匙必须是**创建时那把**，否则不该发出请求。

### 6.5 🔴 但有两件事惰性做不到（需后台协调器）

| 需求 | 为什么惰性不够 |
| --- | --- |
| **回调 `callback_url`** | 契约要求"状态**实际变更**时推送"。若调用方不轮询，惰性实现下回调永不触发 |
| **`execution_expires_after` 看门狗** | 契约要求超时置 `expired`。不查就永远卡在 `running` |

⇒ 需要**一个可选的单实例后台协调器**（`reconciler`）：

- 对**未终态且带 `callback_url` 或已超时**的任务，按固定间隔批量查上游；
- ⚠️ **协调器必须持有同一把钥匙** —— 它没有调用方请求可借，所以要么由渠道注册本次运行期的
  凭证，要么该任务只能等到调用方自己来查。**这是 (b) 带给协调器的额外约束**
  （也是"默认关闭"的又一个理由）；
- 状态变更 → 组装成**查询接口响应体形状** → `POST callback_url` → **5s 无确认重试，最多 3 次**；
- 到 `execution_expires_after` → 置 `expired` 并推送；
- **推送状态不含 `cancelled`**；
- 多 worker 下用 Redis 锁/单实例选主去重，避免重复推送。

> 默认**关闭**（`RECONCILER_ENABLED=false`）：纯轮询型接入方不需要它，
> 开启它意味着服务端要主动出站（需过 SSRF/白名单，见 §11）。

### 6.6 列表

`GET /tasks` → `{"items": [...], "total": N}`，仅含**本服务创建过的**任务，
且**只列本次凭证指纹相符的** —— 索引要建在 `(provider, credential_id)` 上，
只按 `provider` 过滤会把同一渠道下**另一把钥匙**的任务列给对方。

## 7. 并发、幂等与容量

| 议题 | 做法 |
| --- | --- |
| 并发闸门 | **槽位从创建占到终态**（不是创建返回就释放）。上限来自 `X-Channel-Options.max_concurrency`，超限**排队而非失败**，日志显式打印 `UPSTREAM FULL (attempt i/n)` + 退避 |
| 幂等 | 上游无 `Idempotency-Key` 时，按"请求指纹 + 时间窗"在任务表去重，避免调用方重试导致重复计费（aivideomaker 官方线**有** `Idempotency-Key`，优先透传） |
| 429 分流 | 先看 `error.code` 区分**配额限流**（退避+扩容有效）与**突发保护**（退避有效、扩容无效），再决定重试 |
| 重试纪律 | **只对可确认"请求被拒"（4xx）重试**；5xx / 超时 / 不可达一律不重发 —— 重发即可能二次计费（沿用 image-adapter 的窄通道设计） |
| 可观测 | `GET /healthz`（含队列深度、闸门占用、任务表后端类型） |

### 7.1 上游限流：降频优先、主动限速、429 全局冷却（2026-09-13 新增）

**背景**：上游对**任务查询接口**按 **IP** 限 60 次/分钟，超限回 429 + `Retry-After`
（`docs/upstreams/aivideomaker-official-api.md` §6）。"按 IP" 这个限定词决定了实现形状 ——
配额的计量主体是**出口身份**，不是 Key、不是 `provider`、也不是 worker 进程。
三条推论与对应的错误做法见上游契约 §6.1。决策记录见 `ADR-008`。

> ⚠️ 上表"429 分流"一行说的是**方舟原生**的建议（先看 `error.code` 区分配额限流与突发保护）。
> aivideomaker 官方线**不给 `error.code`**，只给 HTTP 429 + `Retry-After` ⇒ 本层对该上游
> 无法做那种分流，靠的是"主动限速 + 冷却"这两条不依赖错误码的手段。

**降频优先于退避。** 五种手段按"减少上游请求数的有效性"排序：

| 层 | 手段 | 效果 | 实现 |
| --- | --- | --- | --- |
| ① | 终态任务本地作答 | 0 次上游请求 | `tasks.get` 开头（原有） |
| ② | **短 TTL 结果缓存** | 窗口内重复查询 0 次上游请求 | `TaskService._query_cache`（默认 2s） |
| ③ | **single-flight 合并** | N 个并发查询 → 1 次上游请求 | `TaskService._inflight` |
| ④ | 主动令牌桶（按 origin） | 把"事后 429"变成"事前排队 / 让路" | `adapter/ratelimit.py` |
| ⑤ | 429 全局冷却 | 踩线后整个出口立刻刹车 | `transport.py` + `note_rate_limited` |

②③ 是主力：调用方的轮询间隔通常远密于上游限额，**在本地消化掉重复查询**比
"发出去再退避"有效得多。降频的观测量是 `task.query.count`（记录里的
`upstream_report.query_count`，2026-09-16 起只上报、不进响应体）——
它计的是**真实上游查询数**，缓存命中不计入，所以能直接回答"省了多少次"。

**为什么不能只靠 429 事后退避**：被动退避只在已经违规之后才起作用，而那次违规还带一次重试 ——
60/min 的硬顶下，重试把请求数放大到配额**之上**，表现为"永远卡在 429"。
这正是旧实现的行为（429 后硬等 10s 再重试，最多 3 次）。

**出口形状**：本地拦截与上游 429 都是 **429 + `Retry-After`**（契约里 429 只有一种形状），
`error.code` 用 `RateLimitExceeded.ModelAccountRpmExceeded`；但 message 说清**是谁在限**
（`locally` vs 上游），否则排障会去查错方向。
`Retry-After` 的取值口径：上游给了就**照传原话**；本地桶算出的用向上取整。

**配置**（默认值即生产口径，逐项理由见 `.env.example`）：

| 环境变量 | 默认 | 说明 |
| --- | --- | --- |
| `RATE_LIMIT_ENABLED` | `true` | 关掉就只剩被动退避（启动会告警） |
| `RATE_LIMIT_QUERY_RPM` | `30` | 上游 60/min 的**一半** —— 给同出口的其它消费者留余量 |
| `RATE_LIMIT_QUERY_BURST` | `5` | 突发取小：上游窗口实现未知，避免边界双倍突发 |
| `RATE_LIMIT_WAIT_SECONDS` | `3` | 无令牌时的排队上限，超出即 429 |
| `RATE_LIMIT_COOLDOWN_MAX_SECONDS` | `120` | 429 冷却封顶（截断会告警） |
| `RATE_LIMIT_RETRY_BUDGET_SECONDS` | `1` | 429 原地重试的等待上限 |
| `QUERY_CACHE_SECONDS` | `2` | 同一任务的查询缓存窗口（降频主力） |
| `RATE_LIMIT_STORE` | 空 | `process` / `redis`；**空 = 跟随 `TASK_STORE`**（多副本少配一个旋钮） |
| `RATE_LIMIT_STORE_URL` | 空 | redis 地址；空则回落 `TASK_STORE_URL` |
| `RATE_LIMIT_KEY_PREFIX` | `ratelimit` | 多个部署共用同一 redis 时必须区分 |
| `RATE_LIMIT_REDIS_TIMEOUT_MS` | `500` | 单次 Redis 操作超时（刻意很短） |
| `RATE_LIMIT_FAIL_MODE` | `open` | 后端不可用时：`open`=退回进程内桶 / `closed`=拒绝 |

**可观测**：`/healthz` 的 `rate_limit` 块给 `scope` / `rpm` / 每个 origin 的剩余令牌与
冷却剩余、以及被拦计数。本地拦截**不产生** `upstream.call` span —— 因为**没有发出调用**，
伪造一条会让上报里"发过的请求"比真实多（与"没收到应答就不许写状态码"同一条纪律）。

#### 桶放在哪：`process` 还是 `redis`（决定配额是否跨副本共享）

配额属于**出口身份**而不是进程 ⇒ 桶**必须跨进程**才是对的。两个后端：

| `RATE_LIMIT_STORE` | 语义 | 适用 |
| --- | --- | --- |
| `process`（默认） | 进程内状态，`scope=process` | 单副本 ⇒ 实际配额 = 该进程的 rpm |
| `redis` | **共享桶**（两个 Lua：取令牌 / 设冷却），`scope=shared` | 多副本 / 多 worker ⇒ **所有进程合起来**才是配置的 rpm |

🔴 **未显式配置时跟随 `TASK_STORE`**：`TASK_STORE=redis` ⇒ 桶也用 redis。
多副本部署本来就必须把任务表放到共享存储上（§6.2），这条推断省掉一个要配的旋钮，
也少一个"任务表共享了、限流桶忘了共享"的错配机会。

🔴 **Redis 后端用服务器时间（Lua 里的 `TIME`）而不是本地时钟**：多副本的本地时钟必然漂移，
用它算令牌补充会让各副本算出**不同**的配额 —— 那属于"看起来能用、其实配额是错的"那类缺陷。

**后端不可用时的行为**（`RATE_LIMIT_FAIL_MODE`，默认 `open`）：

| 取值 | 行为 | 为什么 |
| --- | --- | --- |
| `open`（默认） | 退回**进程内桶**：仍然限速、只是不再精确；连续失败 3 次后**短路 5s**，避免每个请求都去等一个连不上的 Redis | 配额超了是**软**故障（退避即可，上游还有 429 兜底）；把整个服务的查询打死是**硬**故障 |
| `closed` | 拒绝请求 | 把 Redis 当**可用性硬依赖**（这是显式选择，不是默认） |

⚠️ **降级绝不静默**：`/healthz` 的 `backend.ok=false` + `backend.degraded=true` + 原因，
并且 `scope` **如实退回 `process`** —— 此刻它确实不再是共享的。

> 仍在 `process` 模式（或正处于降级）时的替代方案：把 `RATE_LIMIT_QUERY_RPM` 按进程数
> **整除**做静态分摊（3 副本 × 1 worker、希望整体不超 30/min ⇒ 每进程配 10）。
> 代价是某副本故障时其余副本不会接管那份额度 —— 这对限流是**有利**的（更保守）。
>
> 桶的键前缀可用 `RATE_LIMIT_KEY_PREFIX` 区分：**多个部署共用同一个 redis 时必须设置它**，
> 否则它们会共享桶（若它们在同一出口 IP 上，共享恰好是对的；不在同一出口上则过于保守）。

## 8. 素材与产物

### 8.1 入站素材

三种输入路径（`seedance-api-reference.md` §7.3）：公网 URL / Base64 data URI（**仅图片**）/
素材 ID（`asset://`，需加白）。限制：图片 ≤9 张且单张 ≤30MB、视频 ≤3 段且每段 ≤50MB（2–15s）、
音频 ≤3 个且每个 ≤15MB、请求体 ≤64MB。

**类型判定按 magic bytes 嗅探，不信扩展名或 Content-Type**（`adapter-playbook.md` §10 既有教训：
`.jpg` 结尾、`Content-Type: image/jpg` 实际是 PNG）。

### 8.2 产物出站（已实现）

`adapter-playbook.md` §5 要求：**上游产物 URL 常需鉴权或短有效期 ⇒ 应能转存到自有存储**，
不要直接透传上游预签名地址。

**开关在渠道上（逐渠道）**：`X-Channel-Options: {"rehost": true}`，默认 **false**。
默认关闭的理由：aivideomaker 官方线产出的是**公开 24h URL**，与原生 Seedance 语义一致，
透传即可，多一跳只增加失败面。开启的场景是「产物需鉴权」或「有效期短于调用方预期」。

| 项 | 实现 |
| --- | --- |
| 触发点 | 只在**成功终态**做，且同一产物只做一次（`rehost_result.ok` 已存在则跳过） |
| 对象名 | `sha256(产物URL)[:24] + 扩展名` ⇒ **重复转存幂等**，多次查询不会堆副本 |
| 存储后端 | 默认 **local**：写 `MEDIA_DIR`，由本服务 `GET /files/<name>` 对外提供（零依赖）<br>S3/MinIO 留作扩展点（实现同样的 `store()` 语义即可，见 `media.py`） |
| 对外地址 | `content.video_url` 换成**自有地址**；上游原地址留在 `rehost.upstream_url` 可查 |
| 需配 `PUBLIC_BASE_URL` | 不配则返回**相对路径** `/files/<name>`，并在 `warnings` 里如实说明 |
| 大小上限 | `REHOST_MAX_BYTES`（默认 512MB），超了拒绝下载 + warning，**不把内存打满** |
| 落盘原子性 | 先写 `.part` 再 `replace` ⇒ 另一半读到的要么没有、要么是完整文件 |
| 名字即防线 | `/files/<name>` 只接受 `^[a-f0-9]{16,64}\.[a-z0-9]{1,5}$`，挡路径穿越 |
| 失败降级 | 抓不到产物 ⇒ **不改变任务结果**（仍 `succeeded`），给上游地址 + `warnings` |

> **为什么转存在引擎而不是脚本里做**：它不需要任何上游语义知识（下载一个 URL、存下来、
> 换个地址），而且能避免为了它给沙箱脚本开网络能力（脚本至今只能经 `ctx` 触达基础设施）。
> 这与 §5.2 里预留的 `ctx.upload_asset` 相比是**更保守的选择**。

其余回填规则不变：

- `content.video_url` 放 mp4，非 mp4 容器放 `content.file_url`；
- `resolution`/`ratio`/`duration`/`frames` **回填上游实际产出值**，不是请求值；
- `usage` 口径：上游按 credit 计费、Seedance 按 token ⇒ **不伪造**（`playbook` §5）。
  默认 `completion_tokens = total_tokens = creditsCharged`（1 credit = 1 token 当量），
  换算倍率由渠道选项 `credits_per_token` 覆盖。**此项待裁决**（控制面计费依赖它，见 §15）。

## 9. 计费护栏

三条（`adapter-playbook.md` §8）：

1. **默认档位保守**：模型名映射到上游档位时**默认选便宜档**，高价档必须调用方显式要求。
2. **就近吸附可能跨档**：`duration: 8` 吸附到 `10` 可能跨进计费区 ⇒ 在 `warnings[]` 里**明确提示跨档**，
   并提供 `prefer_cheap` 类开关。
3. **`dry_run` 是一等公民**：跑完完整翻译 + 素材转存后返回**将要发出的 payload**，**不提交上游**。

### 9.1 支出上限为提交前置条件（aivideomaker 官方线）

官方线**提交即计费、无免费窗口**，且**上游没有任何计费前闸门**（✅ 2026-09-13 用户确认：
文档只列 `key` / `Content-Type` / `webhookUrl` 三个头，越界信封是**事后告知**的
`{"status":"FAILED","message":"Insufficient credits"}`）⇒ **支出上限完全由本层强制**。见 `ADR-004`。

三道闸门，全部在**发出上游请求之前**：

| # | 闸门 | 行为 |
| --- | --- | --- |
| 1 | 拿不到 `max_credits` | **400** |
| 2 | 本地估算出的积分 > 上限 | **400** |
| 3 | 动态计价、算不出成本 | **默认 400**，必须显式 opt-in |

上限来源（请求级**只能收紧**，不能放宽渠道级）：

| 优先级 | 来源 |
| --- | --- |
| 1 | 请求体 `extra_body.aivideomaker_max_credits` |
| 2 | `X-Channel-Options: {"max_credits": N}`（渠道级天花板） |

两个专给"动态计价模型"（`seedance20`）用的**渠道选项**：

| 选项 | 作用 |
| --- | --- |
| `credit_table: {"seedance20": 12}` | 渠道给出**每秒费率** ⇒ 恢复可估，回到闸门 2。计费知识本来就属控制面（D1） |
| `allow_unpriced: true` | 显式接受"成本不可在提交前验证"；放行，但**在 `warnings` 里如实说明** |

请求级等价物：`extra_body.aivideomaker_allow_unpriced`。

**估算值只用于拒绝，不用于计费** —— 真实扣费以上游返回的 `creditsCharged` 为准
（真实冒烟实测：本地估算 15，上游 `creditsCharged` **也是 15**）。
`0` 是合法上限（等于禁止一切提交）。

### 9.2 dry-run 的开关位置 —— 需你裁决

`adapter-playbook.md` §8 建议用**协议无关的请求头**（`X-Avm-Dry-Run: 1`），
而 D1 说"配置来源全部经 11 个头"。两者可以同时成立——dry-run 不是渠道配置，是调试开关：

| 选项 | 说明 |
| --- | --- |
| **A（推荐）** | 新增第 12 个**可选**头 `X-Dry-Run: 1`（不参与渠道配置语义，不进渠道配置界面） |
| B | 放进 `X-Channel-Options: {"dry_run": true}`（严格保持 11 头） |
| C | 只用请求体键 `aivideomaker_dry_run: true`（对火山 SDK 最友好，但对"通用调试"不通用） |

建议 **A + C 同时支持**（头用于人肉调试，体键用于 SDK 调用）。

## 10. 错误映射

### 10.1 出口信封（Seedance 形状，逐字）

```json
{"error": {"code": "InvalidParameter", "message": "…", "param": "resolution", "type": "InvalidRequest"}}
```

> 与 `videos/src/ark_compat/app.py::_ark_envelope` 现行输出一致，照搬不重新发明。

### 10.2 上游错误 → Seedance `error.code` + HTTP（aivideomaker 官方线）

| 上游 `errorCode` | `error.code` | HTTP |
| --- | --- | --- |
| `AUTH_FAILED` | `AuthenticationError` | 401 |
| `INVALID_MODEL` / `INVALID_PAYLOAD` | `InvalidParameter` | 400 |
| `INSUFFICIENT_CREDITS` | `AccountOverdueError` | 403 |
| `BUDGET_EXCEEDED` | `QuotaExceeded` | 429 |
| `IDEMPOTENCY_CONFLICT` | `InvalidParameter` | 409 |
| `RATE_LIMITED` | `RateLimitExceeded.ModelAccountRpmExceeded` | 429 |
| 本地：无支出上限 | `InvalidParameter`（message 点明 budget guard） | 400 |
| 本地：参考类素材能力缺失 | `InvalidParameter`（message 指明 `content[i]`） | 400 |
| **上游不可达**（连不上 / 超时 / 连接中断） | `UpstreamUnavailable` | 502 |
| 上游 5xx（**收到了应答**） | `InternalServiceError` | 502 |
| 未预期异常（本服务自身的 bug） | `InternalServiceError` | 500 |

**两种 502 必须分开**：`UpstreamUnavailable` = **从没收到应答**（DNS/拒连/超时，没有上游状态码
可用，§10.2 的映射表不适用）；`InternalServiceError` = 上游**回了** 5xx。判据不同，值班动作也不同
（前者查网络/地址，后者查上游状态页）。

两条"绝不裸奔"的保证：

- **传输层失败要转成信封**（`errors.py::upstream_unreachable`）：不转换的话 `httpx.ConnectError`
  会一路冒到 ASGI 层，调用方拿到 `500 Internal Server Error` —— 既不在码表里、也没有可判别信息
  （实测踩到过：假上游端口写错时返回的就是它）。⚠️ 信封里的 message **只给异常类型名**，
  不带 `str(exc)`：httpx 的异常原文含整条 URL，而 URL 可能带凭证查询串。
- **兜底 handler**（`main.py::unhandled_exception`）：任何未预期异常也走同一个信封形状，
  消息里带 `request_id` 供对账，traceback 只进服务端日志。

⚠️ **映射方向是"往契约里已有的 code 收"**：`seedance-api-reference.md` §8 的 code 集合是
调用方已经写好分支判断的那一份，因此**不发明新 code**。上面 `AccountOverdueError` /
`QuotaExceeded` / `RateLimitExceeded.*` 都取自该表；具体落哪一个需按语义复核（见 §15）。

> 呼应 `seedance-api-reference.md` §8 的告警：**429 有两种病因**（配额限流 vs 突发保护），
> 重试策略必须先看 `code`，否则会"加大并发把故障放大"。

#### 10.2.1 SenseAudio 的错误码（`ref_code` → 出口码，2026-09-17 起由错误相位映射）

该上游用 **HTTP 状态码 + 业务码 `ref_code`** 表达错误。非 2xx 的响应体到不了 `*_response`
（§5.1 的错误相位就是为此加的，`ADR-015`），所以映射由脚本的 `create_error` / `query_error`
完成 —— 引擎不解释业务码（那是厂商知识）：

| 上游 `ref_code` | 含义 | 出口 `error.code` | HTTP |
| --- | --- | --- | --- |
| `invalid` | 请求体解析/校验失败 | `InvalidParameter` | 400 |
| `400000` | 参数错误（ratio/resolution/duration/链接） | `InvalidParameter` | 400 |
| `400015` | **已达到最大并发**，稍后再试 | `ServerOverloaded` | 429（带 `Retry-After`） |
| `400001` | 已达到使用限制 / 余额不足 | `QuotaExceeded` | 429 |
| `400900` / `400901` / `400902` | 计费账户不存在 / 已冻结 / 交易过期 | `AccountOverdueError` | 403 |
| `429000` | 请求过于频繁 | `RateLimitExceeded.ModelAccountRpmExceeded` | 429 |
| `429002` | 已达到使用限制 | `QuotaExceeded` | 429 |
| `500000` | "服务繁忙"又注"（非法 model）" | **刻意不映射** ⇒ 5xx 通用规则 `InternalServiceError` | 502 |

两条边界：
- **认不出就不拦**：错误体形状未证实（`ref_code` / `code` / `error.code` 都认），
  都认不出时脚本正常返回，回落上一节的通用映射（`InvalidParameter`）。
  `500000` 自相矛盾 ⇒ 不猜。
- **`Retry-After` 只透传事实**：上游给了用它，其次渠道 `retry_after_seconds`，都没有就不给这个头
  （**不编数字**）；非 429 出口不挂它。

## 11. 安全模型

四道防线**默认全开**（与 image-adapter 同构）：

1. **准入**：`X-Adapter-Key` 恒定时间比较；`ADAPTER_KEY` 未配置则拒绝所有请求。
2. **来源策略**：`ALLOW_INLINE_SCRIPT=false`（**本项目默认即关**）、
   `SCRIPT_PIN_MANIFEST_DIGESTS=true`、`ALLOW_REMOTE_SCRIPT=false`。
3. **AST 沙箱**：白名单 stdlib；禁 `exec/eval/open/getattr/setattr` 及 dunder 访问。
4. **受限 builtins**：无文件/网络/import 能力；基础设施只能经 `ctx` 触达。

`X-Upstream-Url` 过 SSRF 校验（`UPSTREAM_ALLOW_PRIVATE_NETWORK=false` 时拒绝内网目标）。
协调器出站（回调推送）**必须单独过白名单**——它是"服务端主动访问调用方给的地址"，
属用户可控出站，需按目标域名白名单或显式 opt-in 收敛。

## 12. 可观测性

### 12.1 出口与开关

- **日志**是唯一出口，每条带 `request_id`；调用方带了 `x-request-id` 就回显
  （**不加协议里没有的头**），但服务端**总会**有一条 id（没有就生成）——
  否则一次请求的 span 串不起来。
- **上报**走 logfire，`send_to_logfire="if-token-present"` ⇒ **没有 token 就不外发**；
  span 照建，落本地 sink 与日志。**离线校验就建立在这条上**。
- **不做自动埋点**：`logfire.instrument_fastapi()` / `instrument_httpx()` 需要额外的
  `opentelemetry-instrumentation-*` 包（本环境实测未安装，调用即抛），且它们上报的属性集
  **不由我们控制**。上报字段是契约 ⇒ 自己写。
- **装配失败只降级**，不阻止服务启动。`/healthz` 的 `logfire` 报五个字段：
  `configured`（有没有 token）、`emitting`（**真的会外发**）、`ready`（装配成没成）、
  `reason`（为什么不成）、`loguru_bridge`（loguru 桥接的**一行结论**，如
  `on:INFO` / `off: loguru is not importable (ModuleNotFoundError)`）——
  合成一个字段会让运维误判。⚠️ `loguru_bridge` 不是装饰：宿主问"我的 loguru 日志怎么没进
  logfire"时，答案只在这里。
- **两条日志桥，级别默认值刻意不同**：stdlib `logging` 只转 WARNING+
  （本服务自己的 INFO 行基本都有对应 span 覆盖）；**loguru 默认全收 INFO+**
  （`LOGFIRE_LOGURU_LEVEL` 可调）—— loguru 是**宿主应用**的门面，它的 INFO 行没有别处可查。
  loguru **不是**本服务的依赖：不在场就静默跳过并如实报告，**不夺走宿主自己的 sink**。
- **退出前 `flush_spans()`**：批量导出挂在 daemon 线程上且不注册 `atexit`，
  不 flush 就丢掉最后一批 span。放在各资源 close **之后**。

### 12.2 上报什么（字段表就是契约）

🔴 **2026-09-16 起这一节的重要性上升了一个量级**：响应体已收敛为原生字段
（`seedance-api-reference.md` §0.0），所以**下游 task id / 脚本摘要 / 请求响应留档 /
`requested` / `effective` / 降级告警的唯一出口就是这里**。改这一节 = 改排障能力。

| span | 属性 |
| --- | --- |
| `task.create` / `task.query` / `task.cancel` / `task.list` | `task.id` / `task.status` / `task.provider` / `request.id`（**路由层**的三个事实：谁、对哪个任务、最后什么状态）；`task.list` 另带 `task.list.page_num/page_size/total/items` |
| **`task.snapshot`** | **完整任务快照**（每个出口收尾都开一条）：`task.id` / `task.upstream_id` / `task.provider` / `task.credential_id` / `task.model` / `task.model.bare` / `task.model.upstream` / `task.script.ref` / `task.script.sha256` / `task.status` / `task.status.previous` / `task.status.changed` / `task.status.history`（**有界**，只记变更）/ `task.status.changes` / `task.status.unnormalized` / `task.created_at` / `task.updated_at` / `task.expires_at` / `task.execution_expires_at` / `task.callback_url` / `task.query.count` / `task.query.last_at` / `task.query.cache_hit` / `task.query.served`（`upstream`\|`cache`\|`local-terminal`\|`cancel`\|`delete`\|`reconciler`）/ `task.requested`（+`.model/.ratio/.resolution/.duration/.frames`）/ `task.effective`（+`.upstream_model` / **`.model_requested`** / **`.model_map_applied`** / **`.model_map_pattern`** / `.ratio` / `.resolution` / `.duration` / `.tier` / `.estimated_credits`）/ `task.billing.billed` / `task.billing.note` / `task.warnings`（+`.count`）/ `task.unsupported`（+`.count`）/ `task.usage`（+`.completion_tokens/.total_tokens/.credits/.credits_charged/.credits_refunded`）/ `task.artifacts.video_url/last_frame_url/file_url/error` / `task.rehost`（+`.upstream_url` / `.enabled`）/ `task.gate_key` / 正文类：`task.report.request` / `task.report.response`（**创建侧留档，只有创建那条 span 带全文**）/ `task.upstream.raw`（本次查询的上游原文）。⚠️ 查询侧**不重复带**创建原文，只带三个便宜的定位键：`task.report.request.method` / `.url` / `task.report.full_on_span=task.create` —— 单条 `GET` 的 trace 也答得出"创建时打的是哪个端点"，而 36 次轮询不会各带几十 KB |
| `upstream.call` | `upstream.phase`(create/query/cancel) / `upstream.method` / `upstream.url` / `upstream.attempt` / `upstream.idempotent` / `upstream.request.headers` / `upstream.request.body` / `upstream.response.status` / `upstream.response.headers` / `upstream.response.body`（非 JSON 时 `.text`）/ `upstream.duration_ms` / `task.upstream_id` / `task.credential_id`；失败时 `error.type` / `error.message` |
| `script.phase` | `script.ref` / `script.digest` / `phase` / `script.duration_ms` |
| `callback.push` | `callback.url` / `callback.attempt` / `callback.status` / `callback.body` / `task.id` / `task.upstream_id` |

两条硬规则：

1. 🔴 **上游 request / response 一律原文上报**（含 body）。适配层的失败几乎都长在
   "上游到底收到了什么 / 回了什么"上（字段名猜错、`duration` 发成字符串、位置报错被折成 400…），
   只留状态码等于把唯一的证据丢掉。`OBS_REPORT_BODIES=false` 可关正文 ——
   关了就是不出现，**不写空占位**。
2. 🔴 **没有应答就不许有状态码**：连接失败 / 超时时**不写** `upstream.response.status`。
   伪造一个 0 / 502 会让"从没收到应答"与"上游回了 5xx"在 trace 里长得一样，比缺字段更有害。

**上游 task id 到哪拿**：`task.create` 是唯一"刚学到它"的地方（上游的创建响应体里），
在那里补记进任务记录与 `task.snapshot`；`task.query` / `task.cancel` / `upstream.call`
从任务记录带。它与上游对工单、与 `credential_id` 一起回答"这次是拿哪把钥匙建的"。
⚠️ **调用方拿不到它了**（响应体只有原生字段）⇒ 它是"对工单"的**服务端**凭据，
需要给调用方时从 logfire 查、或从上游侧按 `credential_id` 对应的 Key 查。

**三条取值纪律**（`observability.task_snapshot_attributes`）：

1. **拿不到的字段不出现**（而不是写 `0` / `null`）：上报里"没有这个键"与"这个键是 0"
   是两件事，混起来会把对账算错。
2. **同一份数据既展开又整块给**：标量叶子展开成 `task.effective.upstream_model`
   这类键（可直接过滤/告警），同时整块给一份（一次看全）。
3. **`credential_id` 是上报字段，凭证本身永远不是**（前者是 HMAC 指纹，能回答"是不是同一把钥匙"）。

### 12.3 什么绝不进上报

- **凭证**三道：① **源头打码** —— 已知名字的凭证头，以及**值里含渠道凭证的任意头**
  （后者不依赖名字表：`X-Auth-Emit` 允许渠道自选头名，名字表不可能穷举）；
  ② logfire 脱敏回调兜底，**只遮凭证类、其余原文放行**；
  ③ `LOGFIRE_CAPTURE_HEADERS=true` **拒绝装配**（不是警告）。
- 打码**只留长度**（`[redacted 19 chars]`）：不留前缀、不留哈希 —— 低熵 key 的前缀等于半个答案，
  裸哈希可离线爆破（与 `ADR-003` 同一理由）。"是不是同一把钥匙"读 `task.credential_id`。
- body 里**键名是凭证名**的叶子整条遮；但 `completion_tokens` / `total_tokens`
  **必须留原文** —— 遮掉它们等于静默删掉对账字段。
- 超长字符串截断并**显式标注**截掉多少（Seedance 的 `content[]` 里可能有 base64 素材）。

### 12.4 四个已实测的坑（写在这里，别重新踩）

1. 🔴 **`logfire.configure()` 不复用上一次的 `scrubbing=`**（5.1.0 实测）。装配之后谁再
   configure 一次（挂 exporter、改采样、接 instrumentation、测试夹具），就必须带上
   `observability.scrubbing_options()`；漏了默认脱敏就回来 ——
   一句 `"a dog eating a cookie"` 会被**整条替换**成 `[Scrubbed due to 'cookie']`，
   **上报原文静默失效**。
2. **脱敏器会递归进 dict、还会解析 JSON 字符串**，把命中的**叶子值整条替换**。
   默认词表含 `cookie / secret / session / jwt / csrf / credential / api[._-]?key / password`。
   ⇒ body 要**结构化**上报（不要预先 `json.dumps`：预序列化只剩一个叶子，一次命中就全丢）。
3. **`auth(?!ors?\b)` 在 `Authorization` 里匹配到的是 `Auth` 四个字符** ⇒
   凭证名字表里必须有 `auth`，否则回调会把凭证形状当散文放行。
   （另一个反直觉点：**值恰好等于命中词**时脱敏器不调回调、视为安全。）
4. **非原始类型属性导出时是 JSON 字符串**（另附 `logfire.json_schema`），
   断言要过一层 `json.loads`；纯 OTel 的 `InMemorySpanExporter` 里则是真 dict，两者别互相照搬。

### 12.5 验收：离线 + 线上，两件都要做

| 层 | 验什么 | 怎么验 |
| --- | --- | --- |

`scripts/logfire_online_probe.py`（上报通路，需 token、**会真外发**一条合成 span）。

⚠️ **实现中被测试抓到的两个真问题**（记录下来，避免重犯）：

1. **`normalize.py` 写了但没接进引擎** —— 弱校验后缀与首帧归一化在真实请求路径上**根本没生效**。
   表现是上游收到带 `--rs 720p` 的污染提示词。教训：**"实现了"不等于"接线了"**，
   端到端测试必须覆盖"归一化是否真的作用到发出去的 body"。
2. **沙箱禁 `getattr` 是承重墙，不能为了脚本方便而放宽** —— `getattr(x, "__class__")` 能绕过
   AST 的 dunder 检查（字符串字面量不是 Attribute 节点）。所以脚本改用直接属性访问，
   而不是把 `getattr` 加进白名单。

## 16. 部署与扩容

### 16.1 镜像与进程

- **镜像**：`ghcr.io/jushenzhidao/video-adapter`，三个 tag（`<x.y.z>` / `latest` / `sha-<7位>`）
  出自**同一次 build** ⇒ **同一次发布内**三者 digest 必然一致（不一致说明构建了两次）。
  ⚠️ **跨次构建**的 digest 可能不同（COPY 层带检出文件的 mtime）：所以"按 digest 固定版本"
  要在同一次发布里取值，别把两次构建的 digest 当成同一个。要真正可复现需 `--rewrite-timestamp`
  一类手段，本项目没做（收益只是省几次拉取）。
- **发版**：`.github/workflows/release.yml`，**三条入口、一条流水线**：
  | 入口 | 版本号 | 用途 |
  | --- | --- | --- |
  | `push` 到 `main` | **自增 patch**（v0.1.0 → v0.1.1 → …） | 日常路径 |
  | `push` tag `v*.*.*` | 就是该 tag，**不递增** | 需要 minor/major，或契约不向后兼容时由人决定 |
  | `gh workflow run release.yml -f tag=v0.1.0` | 补发指定 tag | 失败重试 / 改了 workflow 后补跑（可重入） |
  ⚠️ 自动递增只覆盖 patch：**对外契约（协议投影、上报字段表）变化时必须走人工 tag** —— 
  那才是"tag 即承诺"的部分。
  逃生阀：commit message 里写中括号的 skip release 标记即可跳过整个 job（纯文档/CI 提交用）；
  它匹配整条 message，所以"描述这个标记"的提交自己也会被跳过 —— 那类提交用第三条入口补发。
  自我触发：模式①会自己 push 新 tag，而 `GITHUB_TOKEN` 推送的事件**不会**触发其他 workflow；
  另有 `actor != github-actions[bot]` 兜底（将来换 PAT 也不自激）。
- **补跑的可见性**：三条入口都要求检出**被发布的那个 ref**（`ref: ${{ inputs.tag || github.ref }}`），
  否则补发旧 tag 会用主干代码构建、并把 `:<version>`/`:latest` 覆盖过去（实测踩到过）。
- **进程**：`gunicorn` + `uvicorn_worker.UvicornWorker`（asyncio）。每条调参的理由写在
  `gunicorn.conf.py` 的 docstring 里，不在这里重复；**不变式**由 `tests/test_gunicorn_config.py`
  钉住（11 项，含跨文件检查，8 组变异自证都会红）。
  ⚠️ worker_class 是 `uvicorn_worker.UvicornWorker`，**不是** `uvicorn.workers.UvicornWorker` ——
  后者在 uvicorn 0.52 起已弃用（实测带 `DeprecationWarning`）。
- 🔴 **2026-09-16 实测：读这份配置时别调这几个参数**（三条都是"调了没用"或"用错层次"）

  | 参数 | 结论 |
  | --- | --- |
  | `worker_connections` | 对 `UvicornWorker` **零作用**（源码里不读它）⇒ 已从配置删除。连接数由 uvicorn/libuv + 内核 `backlog` 决定 |
  | `limit_request_field_size` / `limit_request_fields` | 只作用于 gunicorn **自己的**解析器（同步 worker）⇒ **故意不设**；异步 worker 的头部上限由 ASGI 服务器的解析器决定 |
  | 抬 h11 的 `max_incomplete_event_size` | **无用**：当前解析器是 **httptools**（`uvicorn[standard]` 装了它 ⇒ `http="auto"` 走 `HttpToolsProtocol`），h11 的上限根本读不到。我一度为此加了自定义 worker，实测打在不生效的层，已删除 |

  真实上限（原始 socket 实测，**不走代理**）：**20KB / 70KB / 120KB / 293KB 的请求头全部进到应用层**。
  而 `X-Channel-Options` 的实际用量是"渠道级声明的几条到几十条 `model_map`"（约 1~3KB）
  ⇒ **头部大小不是本服务的瓶颈**，不必再调。
  ⚠️ 排障纪律：给 localhost 探测时 `urllib` 会**读系统 `HTTP_PROXY`**，超大头部会被**代理**
  以 431 回掉 —— 那与 gunicorn 无关。同一请求换**原始 socket** 复测，两次不一致就先怀疑客户端那条路。
- **版本注入**：CI 用 `--build-arg APP_VERSION` → 镜像 ENV `ADAPTER_VERSION`；
  `/healthz.version` 与 OpenAPI 的 version 都读它（值班第一句话是"跑的是哪个版本"）。
  `LOGFIRE_SERVICE_VERSION` 同步注入，让 trace 上的 service version 与镜像一致。

### 16.2 高可用：默认单副本，扩容改两处

| | 默认形态 | 多副本（HA）形态 |
| --- | --- | --- |
| 任务表 | `redis`（与限流桶**共用同一个**；启动即探测，连不上则启动失败） | 同左 —— 默认就已经是共享的，无需额外配置 |
| 入口 | `ports: "${PORT}:8000"` 直连 | **删掉 `ports`**，交给前置代理 / LB（固定宿主端口无法被多副本共享） |
| 副本数 | 1 | `docker compose up -d --scale adapter=3`（任务表与限流桶本来就在 redis 上） |
| 进程数 | `WEB_CONCURRENCY=1` | 仍建议 1（理由见下） |

🔴 **并发闸门是进程内状态**（槽位从任务创建占到终态）⇒ 实际并发上限约为
`副本数 × WEB_CONCURRENCY × max_concurrency`。横向扩容换的是吞吐与可用性，
**代价是闸门不再精确**。上游若按并发硬限流会直接拒绝，那种情况下只能保持单进程
—— 这条写进 `docker-compose.yml` 文末，因为它是扩容时最容易忽略的语义变化。

### 16.3 停机与滚动发布

- 收到 SIGTERM：gunicorn 停止接新连接 → worker 优雅退出 → FastAPI lifespan 关闭 →
  `flush_spans()` 排空上报队列（日志出现 `退出前 flush：已排空`）。
- **时间预算必须成链**：`GUNICORN_GRACEFUL_TIMEOUT=120s` > 在飞上游调用（≤ `REQUEST_TIMEOUT_SECONDS`=60s）
  ＋ flush（5s）；编排层 `stop_grace_period=150s` > graceful_timeout。
  **顺序反了**就等于 SIGKILL 把优雅关机砍掉 —— 表现是"滚动发布时偶发 502 + 丢最后一批 span"。
- 健康检查用镜像自带的 `HEALTHCHECK`（走 `/healthz`，**显式绕开环境代理**：本机实测过
  `HTTP_PROXY` 把回环也代理走、于是"活着"被判成不健康）。compose 里**不重复写一份**。

### 16.4 一条实测记录（别重复踩）

本项目**不挂** gunicorn 的 `worker_exit` 钩子。实测（gunicorn 26.2.0）：
① 它在 worker **自回收**时会触发，但 gunicorn 自己已经打了 `Worker exiting (pid: …)`，钩子只是重复；
② master 收到 SIGTERM 的关机路径上 worker 由信号处理器直接退出，**走不到** `Arbiter.init_process()`
的 `finally` ⇒ 钩子不触发（恰恰是最该看到的时刻）；③ worker 进程里 `worker.exitcode` 尚未由 master 回填
（实测打印 `?`）。⇒ 停机可见性放在**应用自己**那一层（`flush_spans()` 打的那行），不依赖 gunicorn 内部时机。
