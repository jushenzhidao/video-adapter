# ADR-008: 上游限流 —— 降频优先、主动限速、429 全局冷却

## Status
Accepted (2026-09-13)。背景是上游契约 §6 给出了一条此前不知道的信息：
**任务查询接口按 IP 限 60 次/分钟**，超限回 429 + `Retry-After`。

## Background

旧实现只有**被动退避**（`transport.py`）：收到 429 就读 `Retry-After`、硬等
（单次封顶 10s）、最多重试 3 次。当时拿不到上游的限流契约，"429 了就退避"
是能写出来的最好策略。

契约到手后，三个问题暴露出来：

1. **重试会把请求数放大到配额之上**。60/min 是硬顶，每次 429 还带一次重试 ⇒
   发出去的请求数超过配额 ⇒ 下一个窗口继续 429。表现出来就是"永远卡在 429"。
   主动限速必须**前移**到发出之前。
2. **"按 IP" 曾被当成"按请求"**。配额属于**出口身份**：既不是 Key，也不是 `provider`，
   甚至不是某一个 worker 进程。由此三条推论（细节见上游契约 §6.1）：
   （a）桶键必须是上游 origin；（b）额度是**共享**的，本服务看不到同一 IP 上别的消费者
   用了多少 —— 吃满 60 等于把余量留成 0；（c）429 是**全局**信号，一个请求踩线意味着
   整个出口已被盯上，冷却必须作用于该 origin 的所有后续查询。
3. **出口的 429 不带 `Retry-After`**。调用方拿到 429 却不知道该等多久 ——
   而这段信息上游本来就给了，在 `raise_for_status` 里被丢掉了（`UpstreamResult.headers`
   里一直有它，只是没人往出口搬）。

## Decision

**降频优先于退避**（减少请求数 > 事后让步），五层按"减少上游请求数的有效性"排序：

| 层 | 手段 | 效果 |
| --- | --- | --- |
| ① | 终态任务本地作答 | 0 次上游请求（原有行为） |
| ② | **短 TTL 结果缓存**（默认 2s） | 窗口内重复轮询 0 次上游请求 |
| ③ | **single-flight 合并** | N 个并发查询 → 1 次上游请求 |
| ④ | 主动令牌桶（按 origin 分桶） | 把"事后 429"变成"事前排队 / 让路" |
| ⑤ | 429 全局冷却 | 踩线后整个出口立刻刹车 |

配套决定：

- **默认配额 30/min**（上游 60 的一半）。依据是推论（b）：额度共享，吃满等于零余量。
- **突发额度取 5 而不是 60**：上游的窗口实现未知，固定窗口在边界会放行双倍额度 ——
  一次放出 60 个请求是"必然踩线"的写法。
- **只对查询计时**：契约只对查询接口声明了限额，创建 / 取消不计入配额
  （不替上游扩大解释；那两者也已被并发闸门管住）。但它们的 429 仍回灌冷却。
- **429 冷却期内不排队**，直接 429：上游已明确说"别来了"，排队只会把连接堆在这里，
  等到的仍然是 429。
- **429 原地重试仅限 `Retry-After ≤ 1s`**：窗口刚开始滚动时能透明恢复；
  大值原地等毫无收益且占着连接 —— 那种情况该让调用方按 `Retry-After` 退避。
- **冷却上限 120s，且截断必须可见**（warning + 出口值仍是上游原话）：
  静默截断会让人以为"上游让等多久就等多久"。
- **本地拦截也回 429 + `Retry-After`**，但 message 里说清是 `locally`（是谁在限）——
  否则排障会去查上游配额，而那里什么都没有。
- **多副本用"静态分摊"**（把 rpm 按进程数整除），**不假装共享桶**；
  `scope` 字段与启动告警把这件事显式化。

## Consequences

- **正面**：限流从"事后发现"变成"事前计划"；调用方的轮询风暴在本地被消化（②③），
  真正打到上游的请求数大幅下降。
- **正面**：调用方拿到**可执行**的 `Retry-After`（本地桶算出的或上游原话），
  不必自己猜间隔 —— 猜小了会持续撞线。
- **正面**：`upstream_report.query_count` 现在是一个**可信的降频指标**：它计的是真实上游
  查询数，缓存命中不计入 ⇒ 可以直接回答"省了多少次"。
- **负面**：任务状态更新最多延迟 `QUERY_CACHE_SECONDS`（默认 2s）。对分钟级的视频生成
  可忽略，但它**改变了本仓库既有测试的节奏** —— `tests/test_engine.py` 与
  `tests/test_persistence_sqlite.py` 现在必须显式把缓存关掉（它们测的是链路语义与持久化）。
  "加了缓存要让两个测试文件改夹具"本身就是这类改动的典型信号，值得记住。
- **负面**：多副本下实际配额 ≈ 进程数 × `RATE_LIMIT_QUERY_RPM`。已用 `/healthz` 的
  `scope`、启动告警、静态分摊把它变成**显式配置问题**，而不是静默失真。
- **已实现**（同日追加，用户指令「共享 Redis 桶 抓紧实现」）：`RATE_LIMIT_STORE=redis`
  给出**跨进程共享桶**（两个 Lua 脚本 + **Redis 服务器时钟**；用本地时钟会让多副本算出
  **不同**的配额）。当初那条"要先独立决策 fail-open/fail-closed"没有继续悬着 ——
  它**落地成了配置**：`RATE_LIMIT_FAIL_MODE` 默认 `open`（后端不可用 ⇒ 退回进程内桶：
  仍然限速、只是不再精确；连续 3 次失败短路 5s；`/healthz` 如实报 `degraded` 且
  `scope` 退回 `process`），要硬依赖就配 `closed`。
  多副本的"静态分摊"从唯一手段降为 `process` 模式（或降级期间）的替代方案。
  另外**未配置时跟随 `TASK_STORE`** —— 多副本本来就要把任务表放共享存储，
  这条推断少一个旋钮、也少一处"任务表共享了、桶忘了共享"的错配。
- **边界**：本 ADR 不改上报字段表（ADR-006）。本地拦截**不产生** `upstream.call` span，
  因为没有发出调用 —— 伪造一条会让上报里"发过的请求"比真实多，与"没收到应答就不许写
  状态码"是同一条纪律。它记在日志与 `/healthz` 计数器里。
