# ADR-003: 异步任务与凭证绑定，存指纹不存明文

## Status
Accepted (2026-09-13)

## Background
异步任务与同步调用有一个本质差别：**任务要在几天后回查，而回查时带哪把钥匙并不确定**。

两个事实都来自上游契约本身：

1. **接口要求**：`GET /api/v1/tasks/{id}` 必须带 `key` 请求头；
2. **可见性也按钥匙分**：上游的任务列表只返回**当前 API Key 名下**的任务 ——
   上游侧的任务归属就是"那把钥匙"，既不是我们的 `provider`，也不是我们的渠道。

⇒ 于是"认出这次请求带的是哪把钥匙"这件事必须由我们自己做。

同时有一个反向约束：**凭证不能落盘**（密钥不入库是既有纪律）。

## Decision
任务记录里存 **`credential_id` = 创建时那把 Key 的指纹**：

```
credential_id = HMAC-SHA256(TASK_KEY_FINGERPRINT_SECRET, <caller's key>)
```

- 算法用 **HMAC 而不是裸 sha256**：API Key 是**低熵可枚举空间**，
  裸哈希可被离线爆破（拿到库就能反推候选 key）；HMAC 还要求攻击者知道服务端 secret。
- **永不落盘明文 Key**。
- 查询/取消时：算本次请求所带 Key 的指纹 → **与记录不符 ⇒ 本地 404，根本不发上游请求**。
- 列表按 `(provider, credential_id)` 过滤 —— 只按 `provider` 会把同渠道另一把钥匙的任务列给对方。
- 缺 secret 时退化为裸 `sha256`，**记录 `credential_algo` 并在启动时打 warning**（不静默）。

### 为什么必须本地拦
放行到上游就是"用错的钥匙去查"，返回的 404/空**无法区分**"任务真没了"与"钥匙不对"；
更糟的是把跨凭证隔离交给了别人的实现去兜。

## Consequences
- **正面**：跨凭证读取在本地就被挡住，且不泄露"该任务存在但不属于你"。
- **正面**：脚本层看不到也不需要 Key（凭证由引擎作为请求头注入）⇒ 翻译层测试不需要任何真密钥。
- **负面 / 运维注意**：**轮换 `TASK_KEY_FINGERPRINT_SECRET` 会让所有存量任务读不出**
  （算出的指纹与记录不符 → 404），最长影响一个任务保留期（7 天）。
  当前只支持单 secret；是否做双密钥验证窗口见 `OPEN-DECISIONS`。
- **负面**：钥匙轮换后**旧任务只能用旧钥匙查** —— 这是上游的归属语义，不是本项目的缺陷。
  **不要**为了"让旧任务还能查"把 Key 快照进库（凭证落盘 + 轮换后同样失效，双重错）。
- **传导**：后台协调器（回调推送 / 超时看门狗）受同一约束 ——
  它没有调用方请求可借钥匙，所以只能做本地可判定的事；真正的上游回查仍由调用方主动 `GET` 触发。
