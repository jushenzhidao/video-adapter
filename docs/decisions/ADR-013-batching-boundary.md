# ADR-013: 攒批（batching）**不在本层做** —— 边界归 atask-service

## Status

Accepted (2026-09-16)。**用户决定：「异步攒批未来放到 atask-service 吧」。**

## Background

诉求是「能否攒批提交」——把客户端突发的多次创建请求攒成一批再发，用于削峰、
让放行节奏可控。参考物是 **stask-service**：它有成熟的攒批实现
（`app/services/batching.py`：「攒够 N 条或等够 T 秒」两个触发器 + 一个放行点，
`LUA_BATCH_CLAIM` 原子摘取整批成员，sweep 兜底超期未放行）。

关键事实：**这项能力在参考物那里已经存在，并且已经被移植过一次**。atask-service
的 `ADR-011-batch-release-gating.md`（2026-09-13 Accepted）写明是"跨仓库参照
stask-service 的 `batching.py` / `dispatch.py` **同构移植**"，落点为「把**上游提交**
从受理时刻解耦」。

也就是说，本 ADR 要回答的不是"怎么实现攒批"，而是"**它该落在哪一层**"。

## Decision

### D1. 本层不实现攒批，且不引入任何批次概念

不新增攒批相关的请求头、响应字段、错误码、状态。原因不是"没时间做"，而是下面
三条硬约束（见 §Why）。

具体禁令（未来改这里之前先回来读本节）：

1. 响应契约仍由 `ADR-011` 独裁：`POST` **逐键只回 `id`**。不因"攒批需要回传批次状态"
   而在响应体里加 `batch_key` / `batch_state` / `scheduled_at` 一类字段。
2. 不新增 `X-Batch-*` 一类渠道头。渠道头集合由 `ADR-002` 的断言钉住，
   "顺便加一个"会同时打破契约测试与调用方假设。
3. 不新增"排队中 / 待放行"这类**非原生** `status`。原生状态机是六态
   （`seedance-api-reference.md` §5），批次是**投递时机**，不是任务状态。

### D2. 攒批的落点是 atask-service；本层作为它的**上游之一**被排队

本层对外的路径是 `/api/v3/contents/generations/tasks`（原生 Seedance 异步协议）。
atask 的准入范围恰好是「**只接受异步任务**」，两者天然衔接：接入方式沿用 atask 的
既有约定 —— `upstream_allowlist` 放行本层 host、路径允许放行该前缀，**零渠道元数据**。

对外链路因此是四段各司其职，而不是两层都做同一件事：

```
客户端 ──► atask（受理 / 攒批 / 排队：本地 task_id，等待期不占槽）
         ──► new-api relay（鉴权 + 配额扣减 + 渠道选择）
         ──► video-adapter（本层：协议投影 + max_credits 前置 + 出口限流）
         ──► aiviemaker（上游）
```

### D3. 攒批**不合并请求**，因此它不是"用更少的请求刷更多的量"

atask 的 `ADR-011` §1 已明确「**不做把 N 条合并成一次上游请求**」（上游是约定式
异步接口，没有批量端点）；stask 同样不做。所以：

- 攒批改变的是**什么时候**发起提交，**不改变请求的数量与形态**；
- 它的收益是：削掉提交突发、让同一批一起开始/一起结束、受理不再因并发满而 429
  改为排队；
- 它**不**提升"单位时间内能被**均匀**投放的任务数"（滑动窗口下尤其如此）。

> ⚠️ **但"不合并请求"≠"对超刷无用"** —— 2026-09-16 用户补充，本 ADR 首版把这条写得太绝对。
> 攒批能不能"超刷"，取决于**约束的实现形态**，而不是取决于"请求数有没有变少"：
>
> | 约束形态 | 攒批的收益 | 机理 |
> | --- | --- | --- |
> | **固定窗口** + 计数限额 | ✅ **窗口边界套利** | 窗口末尾放出攒的一批、紧接着新窗口开头再放一批 —— 相邻两批**不占同一窗口的配额**，短期通过量可接近均匀投放的 2×（§6 已记录"固定窗口在边界会放行双倍"） |
> | 滑动窗口 | ❌ 无套利 | 只改变到达节奏，总量不变 |
> | 在途 / 并发限额 | ⚠️ 无益甚至有害 | 批放行的瞬时峰值直接撞并发闸门 |
> | **计费 / 结算延迟 gap**（例："30 分钟结算一次"） | ✅ 把提交**压到结算点之前** | 见下方「结算 gap 型的三条推论」 |
>
> 🔴 推论：当"窗口"或"结算 gap"成立时，攒批**必须升级为「deadline 对齐窗口边界」**。
> stask / atask 现有的 T 触发器是"**自首个成员起 T 秒**"的**相对**窗口 ——
> 对齐到绝对时刻（窗口边界 / 结算点）才是这类套利的落地要点。
>
> **前提**：本层已知契约里只有"**任务查询**按出口 IP 限 60/min"，而**提交侧的闸门不存在**
> （`ADR-004` 已确认：上游没有计费前闸门）⇒ 套利类型确定为**结算延迟 gap 型**。
> 仍未证实的是 gap 的时长与周期归属、窗口是否固定、以及**结算失败时上游的处置**
> ⇒ 见 `docs/decisions/OPEN-DECISIONS.md`。
>
> 与本层相关的那半条杠杆仍然成立：上游对**任务查询**按出口 IP 限 60/min，
> 提交突发不受它约束 ⇒ **查询侧降频属于本层**（架构 §7.2 四级，已实现）；
> **窗口/结算套利属于 atask**（它决定"什么时候发"）。

#### 结算 gap 型的三条推论（2026-09-16 用户补充：「只要提交成功就能拿到任务」）

这句话与 `ADR-004` 已确认的事实一致 —— **上游没有计费前闸门，提交成功即锁定任务**。
由此有三条推论：第 1 条决定**风险形态**，第 2 条决定**能力该落在哪一层**，
第 3 条决定**真实天花板**。

1. **提交之后不可撤销**。结算时余额/配额不足，任务**已经在跑**；上层能做的只有
   "事前不提交"，**没有事后补救**。于是本地估算（`max_credits`）从"止损栏杆"
   升级为**唯一**的拦阻点。
2. **`max_credits` 的口径不够用**：它是**单请求**上限（"这一次最多允许多少积分"），
   而结算 gap 型套利需要的是**同一结算周期内的累计额度**（"这 30 分钟一共提交了
   多少估算成本"）。本层是**按请求无状态**判断的 ⇒ 这个累计口径**不该也不能**落在本层，
   它属于 atask（已有 Redis 与批次窗口）或 new-api（计费侧）。
3. **真实天花板是「在途/并发」，不是「提交次数」**。刷量的上限 = 上游允许的在途任务数。
   本层 `ConcurrencyGate`（按 `provider:credential_id`，默认 `DEFAULT_MAX_CONCURRENCY=4`）
   正是这一种约束 ⇒ **不做配置就刷不起来**：放行的一批会在本层排队 `QUEUE_WAIT_SECONDS=20s`
   后回 429。调大它属于**渠道配置**（`X-Channel-Options.max_concurrency`），不是改代码。

### D4. 判据：攒批**什么时候没有作用**（甚至起反作用）

攒批要有正收益，需要**三条同时成立**：

1. **约束是「计数 / 速率型」**（按次、按量计数），而不是**状态型**（在途任务数、并发连接数）。
2. **窗口是固定的**（可以对齐边界），不是滑动的。
3. **限额主体是全局的**（对同一个主体统一计数），而不是按出口 IP / 节点分摊的。

任一条不成立，就会出现下表的情形：

| 情形 | 攒批的效果 | 为什么 |
| --- | --- | --- |
| **在途 / 并发限额** | 🔴 **反作用** | 集中放行制造瞬时峰值，直接撞闸门；分散投放反而能持续占满额度。⚠️ 最常见的踩坑 —— 本层 `ConcurrencyGate` 正是这一种 |
| 滑动窗口限额 | ⚪ 零收益 | 只改变到达节奏，总量与平均速率都不变 |
| **提交侧本来就不受限**（本上游的真实情形） | ⚪ 零收益 | 没有要绕的约束。此时唯一可能的收益是"结算 gap 型"，但那是**调度**（对齐结算点），不是"攒够 N 条" |
| 限额按出口 IP / 节点分摊 | 🔴 **可能反作用** | 把本可分散到多个出口的额度**合并成一个瓶颈**；攒批与"多出口分摊"是互斥策略 |
| 调用方需要即时拿到创建结果（同步语义） | 🔴 代价大于收益 | 攒批 = 请求挂起，直接撞调用方超时；本层入口属于这一类 |
| 提交速率本就远低于限额 | ⚪ 零收益 | 纯增复杂度与延迟 |

一句话判据：**"要不要攒批"不是风格问题，而是"你的瓶颈是速率还是状态"的问题。**
用错地方，攒批会把"平稳占满配额"变成"周期性打满然后被拒"。

### D5. 形态差异：为什么"同步任务好像更容易刷"

这是 2026-09-16 的用户观察（「同步任务好像容易超刷」）。观察成立，但**归因不该落在
"同步 / 异步"这个标签上**，而应落在同一组变量 —— 约束形态、槽位形状、结算时点：

| 维度 | 同步形态（stask 服务的上游） | 异步形态（本层投影的上游） |
| --- | --- | --- |
| 约束形态 | 多为**速率型**（rpm / QPS）+ 连接数 | 速率**之外**常有**任务级配额 / 在途上限**（状态型） |
| 槽位持有期 | **请求期间**（秒级～几十秒） | **从创建占到终态**（出片为分钟级）⇒ 同样额度下吞吐差一个数量级 |
| 结算时点 | 通常**即时**（请求返回即扣费、即知成败） | 可能**延后**（结算 gap ⇒ 先欠后结） |
| 风险敞口 | 小：被拒就是立刻 429，重试即可 | 大：提交后**不可撤销**，余额不足时任务已在跑 |
| 可分摊性 | 高：短连接、无状态 ⇒ 易按出口 IP / 账号水平分摊 | 低：任务归属可见（本层还要存 `credential_id` 指纹），分摊后仍被看作同一作业群 |

🔴 **对本层最要紧的是"槽位持有期"这一行**：本层并发槽按"**从创建占到终态**"持有，
所以吞吐上限 ≈ `max_concurrency ÷ 任务时长`。默认 `DEFAULT_MAX_CONCURRENCY=4`、
视频任务数分钟 ⇒ 每分钟不到 1 条的通过能力。**这才是"异步路径看起来难刷"的第一因，
而它是本侧配置，不是上游额度** ⇒ 调大它属于渠道配置（`X-Channel-Options.max_concurrency`）。

反过来也别误以为同步形态"没有约束"：它的单次成本**即时**发生（账单来得快）、
并发上限通常是**硬的**（打满即 429 或超时，没有排队缓冲）、瞬时峰值更易触发**突发保护**
（§6 已注明 429 有两种病因：配额限流与突发保护）。

**统一结论**：约束越是「速率型 + 即时结算 + 短槽位」，节奏操纵（攒批 / 对齐）的空间越大；
越是「状态型 + 延后结算 + 长槽位」，节奏操纵越无力、甚至有害。**同步与异步只是这组变量
的常见取值组合，不是原因本身。**

## Why not in this layer

### 1. 契约：本层的响应体不允许承载批次状态

`ADR-011` 已把响应收敛为原生字段集（创建只回 `id`、查询不含 `model`），消费方是
`new-api`，它按**原生 Seedance 语义**解析。而攒批必须在受理时就告诉调用方
"它还在排队"（stask/atask 都回 `batch_key` / `batch_state` / `scheduled_at`），
并且把**创建失败从 400 推迟到"202 之后"**。放进本层 = 必须撕破 `ADR-011`。

### 2. `max_credits` 是**提交前置条件**，攒批必然把它推后

`ADR-004` 规定：拿不到上游计价上限 → **400**，且判断发生在**发上游之前**。
攒批的本质就是"受理时刻 ≠ 提交时刻" ⇒ 该检查被迫从"请求内"移到"放行时"，
"400 立即拒绝"变成"受理成功、之后才发现"。这是语义降级，不是实现细节。

### 3. 重复建设：同一语义已经有实现且已 Accepted

atask 的 `ADR-011` 具备攒批所需的全部要素：本地 task_id 协议承载批次状态、
`batch_state` 落库（与状态列正交）、**等待期不占并发槽**（否则"一批 N 条 >
在途上限"永远无法成立，而那正是攒批存在的理由）、占槽失败的指数退避 + 抖动重排、
sweep 兜底。做在本层就是同一个语义的第二份实现，且是**契约更差**的那一份。

## Consequences（跨仓库必须对齐的三项）

### C1. 突发会"搬家"到本层入口 —— 两侧并发参数必须一起调

攒批把突发从「客户端 → atask」搬到了「atask → … → 本层」。本层的
`ConcurrencyGate` 按 `provider:credential_id` 限并发
（`DEFAULT_MAX_CONCURRENCY=4`），超出后**排队** `QUEUE_WAIT_SECONDS=20s`，
超时回 `429 ServerOverloaded`。

⚠️ 批次放行 N 条（很可能 ≫ 4）同时到达 ⇒ 若 atask 侧不同时约束放行节奏，
本层会批量 429。**两侧同一渠道的参数必须配套调**（atask 的批次窗口 / 并发 ⇄
本层的 `max_concurrency` / `queue_wait_seconds`），否则表现为"开了攒批，429 反而变多"。

### C2. 本层 429 的语义要按"可重排"消费

本层出口 429 只有一种形状（本地桶或上游 429，带 `Retry-After`）。atask 侧应按其
失败分档**重排/退避**而非记终态。两侧对 `Retry-After` 的理解必须一致。

### C3. `max_credits` 前置检查不受影响

解耦点在 atask ⇒ 本层收到的请求永远是"要发"的请求，`ADR-004` 的前置检查位置不变
（这也是把攒批放在更外层的附带好处：本层语义保持"收到即校验、即发"）。

## Verification（未来落地时的验收口径）

- **本层侧**：断言型测试 —— 本层**不识别**批次头（传入 `X-Batch-*` 时按未知头忽略：
  不进响应、不进上游 body），即"边界没有被越界地补齐"。
- **atask 侧**：攒批 E2E（N 触发 / T 触发 / requeue / sweep 四条路径）打本层的
  假上游，断言 **① 本层不产生 429**、**② 上游实际收到的请求数与 body 符合预期**。
- 🔴 **套利类收益不能用假上游证明**：窗口边界与结算 gap 只存在于真实上游/真实计费链路，
  假上游必然"没有窗口" ⇒ 那种环境里测出的"通过量提升"是**假证据**。这类验证按硬纪律走：
  先用 `dry_run` 把**请求形状**验完，真实提交**只发最便宜档、且发之前先问用户**
  （`ADR-004` 的止损栏杆只做**事前**估算，无法回收已经发生的上游消耗）。
