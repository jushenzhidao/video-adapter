# ADR-015: 上游非 2xx 的错误体经**可选错误相位**映射

## Status
Accepted (2026-09-17)

## Background

相位契约原本只有 `<phase>_request` / `<phase>_response`（`docs/03_引擎架构.md` §5.1）。
非 2xx 的上游应答在 `executor.raise_for_status()` 处就抛了，**在 `*_response` 相位之前** ——
所以脚本**永远看不到**错误体，出口码只能由 HTTP 状态决定（`errors.UPSTREAM_HTTP_TO_CODE`）。

接第二个上游（`senseaudio`）时这条立刻变成实质缺陷：该上游用
**HTTP 状态码 + 业务码 `ref_code`** 表达错误（`docs/upstreams/senseaudio-official-api.md` §5），
于是

| 上游 | 真实含义 | 当时的出口 | 调用方会怎么做 |
| --- | --- | --- | --- |
| `400 400015` | 上游并发已满，稍后再试 | `400 InvalidParameter` | 以为自己的请求写错了，**不改、不退避** |
| `400 400001` | 使用限制 / 余额不足 | `400 InvalidParameter` | 同上（而真实动作是去充值/提额度） |
| `400 400900~902` | 计费账户不存在 / 冻结 / 交易过期 | `400 InvalidParameter` | 同上（而真实动作是找运营方） |
| `429 429000/429002` | 请求过于频繁 / 达到使用限制 | `429`（正确） | — |

⇒ 4 类错误被指向了**错误的排查方向**，而这正是本项目反复强调的那条
（"报错层次错了，排查就会去错的地方"）。

曾有两条候选（见 `OPEN-DECISIONS` 2026-09-17 行）：

1. **渠道级声明表** `X-Channel-Options.error_map: {"400015": "ServerOverloaded"}`；
2. **可选错误相位** `<phase>_error`，由脚本做映射。

## Decision

**采用 ② 可选错误相位**，理由是一条硬约束：要按业务码映射，就必须先从**错误体**里把码读出来，
而错误体的形状（码放在顶层 `code` 还是 `ref_code`、还是 `error` 子对象里）是**厂商知识**。
把它写进引擎 = 服务端持有上游知识（架构 D1 明禁），而且要为一个厂商的形状改动共享代码；
把它放进声明表也一样（表里得写 JSON 路径，迟早要为第二个厂商加第二套语法）。

**相位契约**（对齐既有的六个相位，只加不改）：

| 相位 | 触发 | 输入 → 输出 |
| --- | --- | --- |
| `create_error` / `query_error` / `cancel_error` | 上游回**非 2xx** 时 | `payload` = 上游错误体；`ctx.upstream_error` = `{status, retry_after, headers, phase}` → **要么 `ctx.fail(...)` 抛出精确错误，要么正常返回（= 不拦）** |

三条约束（写进 `executor.py` 的 docstring，并由用例钉住）：

1. **可选**：脚本不声明该相位 ⇒ 行为与从前**逐字一致**（通用映射兜底）。
   `tests/test_engine.py::test_script_without_error_phase_keeps_the_generic_mapping` 钉住这一点 ——
   新增机制不得回流污染既有上游。
2. **不拦就算**：相位正常返回 ⇒ 回落 `raise_for_status`。所以"认不出的业务码"
   由**脚本**决定不拦（`senseaudio` 的脚本对 `500000` 与任何认不出的码都不拦），
   引擎不猜。猜错方向的代价是双向的：把 `error.code` 里的英文错误名当业务码，
   会把"上游 500"说成"你的参数错了"。
3. **绝不用它掩盖上游错误**：错误相位自己抛非 `AdapterError` ⇒ 只记 `log.warning` + 回落。
   一个辅助相位的 bug 不许把真实的上游故障变成 500（与"埋点不得拖垮主流程"同一纪律）。

配套：`ctx.fail()` 增加 `retry_after` 参数。否则脚本没法把上游的 `Retry-After` 带出去，
而"429 一定告诉调用方该等多久"是既有承诺（`ADR-008` 的降频语义与 `errors.py` 的口径）。
**"上游没说"与"上游说等 1 秒"是两件事**：脚本只在拿到上游值、或渠道显式声明
`retry_after_seconds` 时才给这个头，**不编数字**。

## Consequences

- **正面**：上游业务码的映射回到它该在的地方（脚本 = 一个厂商契约的翻译层），
  引擎继续对上游一无所知；加第三个上游时不需要再动引擎。
- **正面**：机制是**纯增量**的 —— 可选相位缺席即老行为，既有上游零风险。
- **负面 / 已接受**：脚本契约从"6 个相位"变成"6 + 最多 3 个可选相位"，文档与
  `PHASES` 校验的口径要跟着更新（漏了会出现"脚本声明了却没实现"的 `channel_config_error`）。
- **负面 / 已接受**：`ctx.upstream_error` 只在错误相位里有值，是个**相位局部**变量 ——
  在别的相位读它恒为 `None`。这一条必须写在 `ctx.py` 的 docstring 里，否则下一个人会当成常量用。
- **未覆盖**：`ctx.upstream_error` 的 `headers` 目前只用于排障（凭证头不在其中，它由渠道层发射，
  从不进响应头归档）。若将来要按上游的某个头做决策，先确认它到底是什么。
