# ADR-012: 模型名**透传**，映射表外置到渠道（精确匹配）

## Status
Accepted (2026-09-16)。**用户决定：「model 映射想个方案做成可配置，要不放请求头？」+
「完全透传：写什么发什么」+「（合法值）t2v/i2v/t2v_v3/i2v_v3/minimax/seedance20/wan27/happyhorse」
+「代码里不改模型值」。** 本文取代 `ADR-009` D6 的机制部分。

## Background

调用方按目标契约写的是**具体 Seedance 模型 ID**
（`doubao-seedance-2-5-260628` / `…-2-0-260128` / `…-1-5-pro-251215` / `…-1-0-pro-250528` …），
而上游只有 **8 个粗槽位**（`t2v` / `i2v` / `t2v_v3` / `i2v_v3` / `minimax` / `seedance20` /
`wan27` / `happyhorse`）。名字那一跳由谁做、怎么做，此前没定。

### 原实现（2026-09-16 删除）与它的代价

`script_store/aivideomaker/video@v1.py` 里有一张模块级正则表，**顺序敏感**：

```python
_MODEL_PATTERNS = ((r"seedance", "seedance20"), …)   # 第一条就吞掉所有含 seedance 的名字
```

| 问题 | 实测后果 |
| --- | --- |
| **顺序敏感**：调换两行即静默错映射 | 5 个不同代次的原生 ID（`2-5` / `2-0` / `2-0-fast` / `1-5-pro` / `1-0-pro`）**全落 `seedance20`** |
| **命中不可见**：连 `warnings[]` 都没有 | 调用方"付费买 A、拿到 B"却查不出原因（只有 `effective.upstream_model` 能看出来） |
| **代价是账单**：见下 | 真上游实测：同一个原生 ID 落 `seedance20` 收 **110 积分**，而同参数 `t2v` 只要 **15** ⇒ **7.3 倍** |
| **闸门失效**：`seedance20` 是上游动态计价、本地算不出 | 支出上限从"提交前可验证"退化成"事后才知道"（须 `allow_unpriced` 才放行） |

> 那次实测我自己按 `t2v` 的 15 积分向用户报了预期，**实际被扣 110** ——
> 预估错误本身就是这个 bug 的产物。

## Decision

### D1. 本层**不改模型值**（默认透传）

`model = <provider>/<model>` 里的 `<model>` 段剥掉 provider 前缀后**逐字**发到上游
`POST /api/v1/generate/{名字}`。合法值 = 上游认识的槽位名。

⇒ 本层**不持有**任何"名字 → 身份"的映射知识（D1 的旧承诺由此真正兑现到模型维度；
与 `ADR-010` 把计费归还 new-api 是同一条思路：**知识归控制面，数据面只执行**）。

### D2. 需要翻译时，由**渠道**声明映射表（`X-Channel-Options.model_map`）

```json
X-Channel-Options: {"provider":"aivideomaker","max_credits":5000,
                    "model_map":{"doubao-seedance-2-0-260128":"seedance20",
                                 "doubao-seedance-1-0-pro-250528":"t2v"}}
```

| 规则 | 内容 | 为什么 |
| --- | --- | --- |
| 落位 | `X-Channel-Options`（**不新开头**） | 它已经装着 `model` / `credit_table` 这类渠道知识；新开头只是多一处要同步维护。别名 `upstream_model_map`（`docs/03` §4.2 曾登记过的名字）同样接受 |
| 匹配 | **精确匹配优先**；键里含 `*` 即为通配模式（`*` 是**唯一**元字符、大小写敏感、`?`/`[]` 字面量）。**无正则、不做"最长匹配"、无歧义分支**：两条通配同时命中 ⇒ 报错 | 它取代的正是"顺序敏感的正则"这一整个失败模式；歧义一律**响亮失败**而不是排序。（**2026-09-16 修订**：原先写的"无通配"改为"只有一个元字符、且不排序"，见文末） |
| 重复键 | **显式拒绝**（**大小写不敏感**判定） | JSON 同名键会静默覆盖，而"哪条生效"直接决定账单；`Wan27` 与 `wan27` 是同一意图，取其一就是猜 |
| 值域 | 必须是上游槽位之一 | 给个上游不认识的値 = 把 400 推到上游，而那时请求**已经带着凭证发出去了** |
| 缺省 | **不映射**：名字本身必须是槽位名，否则 **400**（消息同时列出合法槽位与渠道已配的键） | "兜底到某个槽位"是最坏选项：错名字应当**响亮**，不该变成一张账单 |
| 已撤除的键 | 渠道 `model`（钉住槽位）**2026-09-16 撤除**；遗留该键 ⇒ **`channel_config_error`**（**值合法时也照拒**） | 撤除后不存在"一致就放行"这条语义；静默接受一个"恰好一致的钉住"只会养出"我以为它还钉着"的依赖。要用通配表达"本渠道只跑某个槽位"见文末修订 |
| 可见性 | 命中写进 `effective.model_map_applied` + `effective.model_requested`；**通配另记 `effective.model_map_pattern`** | 响应体已不含 `model`（`ADR-011`）⇒ 这对字段是"我请求的 vs 实际跑的"的判据（另一处是 `dry-run`）。通配能改写模型值 ⇒ 只记一个布尔值回答不了"为什么被改了"，必须记下**命中的模式** |

### D3. 报错分层沿用既有约定

- **调用方传错**（名字既不是槽位、也不在表里）→ 400 `InvalidParameter`，`param=model`；
- **运维配错**（表的值非法 / 重复键 / **两条通配同时命中** / 遗留已撤除的 `model` 键 / 两个别名不一致）
  → `channel_config_error`。两类的**修复人不同**，混在一起会把排查带偏。

### D4. 命中必须可查（对账与排障）

日志/上报里同时能看到"请求的"与"实际发出去的"。这是 `ADR-009` D6 第 5 条
（`model.map.hit`）的落地形态，只是名字更直白。

## Consequences

- **正面**：删掉一类**静默**失败模式（顺序敏感的正则 + 无告警）。
  "我请求的模型"与"实际跑的模型"之间不再有任何隐式跳转。
- **正面**：同一份脚本可服务多个上游；新增上游改**配置**不改脚本（`ADR-009` D6 的目标达成）。
- **正面**：火山原生 ID 不再是陷阱 —— 没配表时**当场 400**（并告诉你缺什么），
  而不是"看起来成功、账单 7 倍"。
- **负面（已接受）**：**"只改 Base URL 与 Key 就能无痛切换"这句话对原生模型 ID 不再自动成立** ——
  渠道必须配一张 `model_map`（或者控制面 new-api 先做名字翻译）。
  ⚠️ 这与"无痛切换"并不冲突：切换本来就是**控制面**的动作，而映射知识正属于控制面。
- **负面**：映射表放在请求头 ⇒ 条数受 **HTTP 头整体大小**限制。它是**渠道级声明**
  （几条到几十条），**不是词库**；真到几百条时再谈"渠道配置持久化"（`OPEN-DECISIONS` 已记）。
- **负面**：表本身可能配错（如把 `1-0-pro` 映到 `seedance20`）。本层**不校验业务合理性**
  （只校验"是不是合法槽位"）—— 那是 `docs/04` §1.2 的推荐内容与运营方的责任。
- **风险**：`dry-run` 与 logfire 是唯一的"事后证据"。若接入方两者都不看，映射发生与否对它不可见
  （`ADR-011` 的既定取舍）。

## 2026-09-16 修订：撤除「钉住槽位」，`model_map` 通配承接

需求方当日两条决定（原话：「要不用 `model_map` 替代吧」＋「`model_map` 兼容下通配」，
配例 `{"*": "<槽位>"}`）：

1. **`X-Channel-Options.model` 撤除。** 它只做一致性断言（不一致 ⇒ `channel_config_error`），
   不承担任何名字转换 ⇒ 与"一个渠道一套配置"的其余部分重复。
   ⚠️ 遗留该键**一律 `channel_config_error`**（值合法时也照拒）：撤除后不存在"一致就放行"
   这条语义，静默接受一个"恰好一致的钉住"只会养出"我以为它还钉着"的依赖 —— 而那个依赖
   已经没有任何代码支撑。
2. **`model_map` 的键支持通配**：`*` 是唯一元字符（大小写敏感，`?` / `[` / `]` 是字面量）。
   三条**不可协商**的护栏：**① 精确优先**；**② 两条通配同时命中 ⇒ `channel_config_error`**
   （不排序、不取最长 —— 那正是本文开头那个 7.3 倍账单的失败模式）；**③ 命中模式可查**
   （`effective.model_map_pattern` → logfire 的 `task.effective.model_map_pattern`）。
3. **通配优先于"名字本身就是槽位名"** ⇒ `{"*": "t2v"}` 是渠道级的"本渠道只跑 t2v"，
   **合法槽位名 `wan27` 也会被改写**。这是明确要的语义（它承接了被撤除的"钉住"能力），
   代价是"我请求 A、实际跑 B" —— 由第 2 条的可见性兜住。
   ⚠️ 它与 `ADR-009` 否掉的"兜底"**不是一回事**：兜底是**本层内置**的默认值（代码里的知识），
   通配是**控制面显式声明**的策略。但**误配的通配确实会静默改写模型值**，这是接受的代价：
   修法是改渠道配置，而不是让本层替它排序或猜。
4. **已同步**：`docs/seedance-api-reference.md` §1.1、`docs/03` §4.2、`docs/04` §6、
   `README.md` 的 `X-Channel-Options` 键表、`adapter/observability.py` 的 `effective` 字段表、
   以及 `script_store/aivideomaker/video@v1.py` 与 `tests/test_aivideomaker_video_v1.py`。
