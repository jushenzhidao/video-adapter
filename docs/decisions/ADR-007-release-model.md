# ADR-007: 发版模型 —— push main 自增 patch，人工 tag 保留给不兼容变更

## Status
Accepted (2026-09-13)。**用户指令：改成"push main 即自增 patch"。**
**部分取代** ADR-006 之后的发版约定（`docs/03_引擎架构.md` §16.1 原写"刻意不做自动递增"）。

## Background
初版把发版定成"只认人工 tag"，理由写在 §16.1：对外契约是**协议投影 + 上报字段表**，
自动递增会把"契约没变"和"契约变了"混成同一条时间线，调用方无法据此判断能不能升。

那条理由本身仍然成立，但它的代价被漏算了：**patch 级的日常改动（修 bug、补埋点、改部署）
每次都要人多做一步打 tag**，而这一步不带来任何判断价值 —— 没有人会为"修了一个日志格式"
去纠结版本号。把判断权与机械动作混在一起，结果是**日常发版被拖慢**，而真正的判断点
（minor/major、契约不兼容）反而因为信噪比下降更容易被忽略。

## Decision
**两条入口、一条流水线**（`.github/workflows/release.yml`）：

| 入口 | 版本号 | 适用 |
| --- | --- | --- |
| `push` 到 `main` | **自增 patch**（`v0.1.0` → `v0.1.1` → …） | 日常：修 bug、补埋点、部署与文档 |
| `push` tag `v*.*.*` | 就是该 tag，**不递增** | 需要 minor/major，或**对外契约不向后兼容** |
| `workflow_dispatch -f tag=…` | 补发指定 tag | 失败重试 / 改了 workflow 后补跑（可重入） |

- **"tag 即承诺"没有取消**：它被收窄到"需要人判断"的那一类变更上（minor/major、契约不兼容），
  恰恰是判断真正有信息量的地方。
- **逃生阀**：commit message 里带中括号的 skip release 标记 ⇒ 整个 job 跳过。
  给纯文档 / CI 自身的提交用。⚠️ 它匹配**整条 message**，所以"描述这个标记"的提交自己也会被
  跳过 —— 那类提交用 `workflow_dispatch` 补发。
- **自我触发防护**：自动模式会自己 push 新 tag。`GITHUB_TOKEN` 推送的事件**不会**触发其他
  workflow，因此不会绕回来；另加 `actor != github-actions[bot]` 兜底（将来改用 PAT 也不自激）。
- **顺序**：镜像先推、tag 后打 ⇒ 构建失败不会留下"有 tag、没镜像"的半成品；
  同 ref 串行（`concurrency`）⇒ 两次 push 不会争夺同一个版本号。

## Consequences
- **正面**：日常发版零人工步骤；patch 号成为"主干推进"的计数器。
- **正面**：逃生阀把"这次不该出版本"变成一次显式声明，而不是靠人记得别推。
- **负面**：主干上每一次非 skip 的提交都会切一个版本 ⇒ 版本号密度上升，
  `latest` 镜像跟着前移。调用方若按 `:<x.y.z>` 固定就没事；按 `latest` 就会跟着跳
  （这本来就是 `latest` 的语义）。
- **负面**：patch 号不再代表"兼容性等级"，只代表"主干又往前走了 N 步"。
  兼容性判断必须看 **Release notes / 是否走了人工 tag** —— 所以人工 tag 那类发布
  要在 notes 里写清不兼容点。
- **边界**：本文不改变 ADR-006 的上报契约，也不改变 tag → 镜像 tag（无 `v` 前缀）的映射。
