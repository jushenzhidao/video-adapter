# ADR-002: 路由逐字等于原生，多上游靠 `model = provider/model` 区分

## Status
Accepted (2026-09-13)。**作废两条更早的方案**（见文末）。

## Background
一个部署要承载多个上游。区分手段有三种候选：

- **A. 路径前缀**（`/{biz}/api/v3/contents/generations/tasks`）—— 路径即命名空间，但路径偏离原生，
  调用方要按渠道改 `base_url`，且多前缀要长期维护。
- **B. 三种前缀同时收敛**（`/api/v3` + `/api/plan/v3` + `/api/v1`）—— 曾一度被认为是"改 Base URL 就接入"的前提。
- **C. 请求体里的 `model` 字段** —— 路径零偏差，但需要一种语法承载上游身份。

关键事实：**控制面（New API）本来就按 `model` 名路由到渠道**。

## Decision
**路径逐字等于原生** `/api/v3/contents/generations/*`（不加前缀、不加路径段），
**多上游靠 `model = provider/model` 区分**，如 `"model": "aivideomaker/doubao-seedance-2-5-260628"`。

`provider` 段的角色是**断言 + 命名空间**，不是凭证来源：

| 规则 | 说明 |
| --- | --- |
| 断言 | `provider` 必须与渠道声明的 `X-Channel-Options.provider` 一致，**不一致 → 400** |
| 为什么需要 | 专门消灭"模型名写错/漏改 → 静默落到别的上游 → **直接付费**" |
| 裸模型名 | 走渠道声明的 provider；渠道未声明 ⇒ 400，**不猜** |
| 命名空间 | 任务键含 `provider`，跨 provider 读任务必须 404 |
| 凭证 | 仍全部来自请求头（D1 不破） |
| 命名取 `provider` 不取 `vendor` | `aliyun-bailian/deepseek-v3` 里阿里是**供给方**而非 DeepSeek 的 vendor；`vendor` 会让人分不清该填厂商还是供给方。**两个轴必须分开：`provider` = API 供给方（进路由），模型出品方不进路由、不进响应** |

### `model` 方案唯一的硬约束
`GET`/`DELETE` 的路径与请求体里**都没有 `model`** ⇒ 渠道身份有两个来源，**两个都要用**：
任务记录（提供 provider）+ 请求头（提供上游地址与凭证）。两者不一致 ⇒ **404**。

## Consequences
- **正面**：路径零偏差，调用方迁移路径最短；数据面**不需要任何渠道注册表**（D1 不破）。
- **负面**：查询/取消侧的渠道身份要靠"任务记录 + 请求头"两处对齐，必须在测试里钉住一致性。
- **负面**：`provider` 必须与渠道 1:1 —— 同一供给方有多条接入线时值取「供给方-线路」
  （`aivideomaker-official` / `-web`），字段名不变。

## 作废记录（供后来者避免重走）
1. **"三种前缀必须同时收敛"** —— 作废。路径主体只有原生一族；多前缀若真需要属**部署层反代**职责，
   不进应用（否则变成要长期维护的路由分支）。
2. **"路径前加 `{biz}` 段"** —— 同样未采纳。它让路径偏离原生、且要求调用方按渠道改 `base_url`。

> 教训：遇到"看起来少了"的地方，先确认它是缺陷还是**刻意的范围收敛**。
