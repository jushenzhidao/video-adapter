# ADR-010: 计费与配额归属 **new-api**，本层不承担计费

## Status
Accepted (2026-09-14)。**用户明确：「本项目不承担计费，后面是配置到 new-api 渠道里的。」**

## Background
本层此前把自己描述成"唯一由本层承担的资金安全责任"（`ADR-004` 的 Consequences 原话），
读起来像是**本层拥有计费职责**。实际部署形态是：本服务作为**上游渠道**接到 **new-api** 后面 ——

```
调用方 → new-api（额度检查 / 扣减 / 用户账单）→ video-adapter（协议投影）→ aivideomaker（真花钱）
```

⇒ 计费发生在 new-api；本层既不该持有单价表，也不该做额度扣减。
但 `ADR-004` 的事实前提**依然成立且不受影响**：**上游提交即计费、无免费窗口、无计费前闸门**。
两件事必须分开：

| 问题 | 归属 |
| --- | --- |
| 向调用方收多少钱、扣谁多少额度 | **new-api** |
| 这次提交会不会把**运营方的上游余额**花掉 | **本层**（唯一能拦的地方：上游不拦、new-api 也拦不到） |

## Decision

### D1. 计费、配额、单价表一律不在本层
本层**不**持有单价、**不**做额度扣减、**不**生成用户账单。
`D1`（服务端不持渠道与计费知识，见 `03_引擎架构.md`）由此从一条自律升级为**部署事实**：
价格与配额在 new-api 侧，本层只认请求头传来的渠道配置。

### D2. 本层在"钱"上只剩两件事
1. **把上游的真实消耗折算成 new-api 能消费的形态** —— 这是**交付义务**，不是计费：
   上游 `creditsCharged` / `creditsRefunded` ⇒ `usage.{completion_tokens,total_tokens}`
   按 `credits_per_token`（默认 1:1）折算，**同时原样保留 `credits` / `credits_charged` /
   `credits_refunded`**，让 new-api 能按自己的口径重算。**不伪造、也不丢原始值**（已实现）。
2. **`max_credits` 作为「上游账户安全栏杆」** —— 它的语义要按此收敛：
   它不是计费，也不是"预算系统"，而是**提交前置的止损开关**：
   拿不到上限 → 400；本地估算 > 上限 → 400；动态计价无法估算 → 默认 400 或显式 `unpriced`。
   全部在**发出上游请求之前**（`ADR-004` 的三道闸门不变，只是**定位**从"资金安全责任"
   收敛为"上游账户栏杆"）。

### D3. `credits_per_token` 是**运营方的定价旋钮**，不是计费实现
new-api 按 token 当量消费 `usage`，因此这个倍率实质上决定了"上游 1 积分折成下游多少 token 当量"。
**倍率配错 = 单价配错**，且它决定的是**运营方会不会亏**，不是调用方的账单。
⇒ 它属于渠道配置（随渠道头走），变更要当**定价变更**对待，不能当普通参数。

### D4. new-api 的前置闸门**不保护运营方**
new-api 在调用方视角确实提供了前置额度检查。但那扣的是**调用方的额度**，
而本层花的是**运营方的上游余额** —— 两者口径可以不一致：
new-api 按自己的渠道定价扣，上游按自己的公式收。

> 🔴 **`max_credits` 关的就是这个差额。** 没有它，一次"new-api 认为便宜、上游认为贵"的提交
> 会直接把差额记在运营方账上，且**在事后对账前无人察觉**。

### D5. 因此要暴露"预估"，而不是只暴露"实收"
`estimated_credits`（提交前本地按官方公式估）与 `creditsCharged`（提交后上游权威）**都要可见**：
- 前者是**给 new-api 渠道定价用的参考值**；
- 两者之差是**定价是否配错的唯一早期信号**。

⚠️ 现状缺口：`estimated_credits` 由脚本算出（在 `ctx.plan` 里）但**引擎从不读**，
响应里也没有 —— **连 dry-run 都不返回**（只回 `requested`/`effective`/`warnings`/`unsupported`）。
⇒ 在 D1 的框架下这不是"可选增强"，而是**运营方配置定价与对账的必要输入**。

## Consequences
- **正面**：本层保持无状态、无价格表、无账户概念，与 D1 一致；换计费系统（不只 new-api）无需改本层。
- **正面**：`usage` 的"token 当量 + 原始积分并列"让 new-api 可以按自己的口径重算，不必信本层的折算。
- **负面**：运营方必须自己维护 new-api 侧的渠道定价表；本层**不校验**它是否与上游真实价格一致。
- **负面**：`ADR-004` 的措辞（"唯一由本层承担的资金安全责任"）会长期误导读者 ⇒ 已在该文加范围指针。
- **风险**：`max_credits` 若被当成"计费系统"来配（例如按用户额度动态下发），会把两件事重新混起来。
  **它应当是一个稳定的、按渠道配置的止损值**，不是按调用方变化的额度。
- **风险**：动态计价模型（`seedance20`）在本层算不出成本 ⇒ 只能靠 new-api 侧定价兜住；
  而它恰恰是单价最高的档（实测 5s/720p = 110 积分，约为 `t2v` 的 7 倍）⇒ 定价配错时**亏得最多**。
